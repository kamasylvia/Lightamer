# PIPELINE — 管线内核（B1-a 地基 + B1-b 执行 + B1-b2 修正 + B1-c 引擎接线 + B1d-a 行带流式 + B1d-b 引擎接线 + B1d-c 探尺寸直流）

B1-a 落的是管线内核的地基：画面与区域的数据类型、模块接口、几何链、
格式协商、分块决策。B1-b 落的是执行：渲染入口、缓存、按行并行、分块
执行、单块下限、按物理内存推导的配额。B1-b2 修的是执行层的四处：逐节点
即时写缓存（峰值不再随链长涨）、分配前淘汰让路、删掉有名无实的单块上限、
写明上限并前置拒绝。B1-c 把渲染接到引擎的作业池上：命令登记启动就返回，
作业去渲，同一对（照片，实例）只留最新一代（见末节「渲染作业」）。B1d-a 落的是整链行带流式：`render_stream` 新入口、双模式规划与执行、输出帧落盘（见「行带流式」）。

darktable 源码引用皆指 `refs/dt-master @ 679d594f5d`（只读上游）。
规则是读源码移植的，代码没有抄一行 C。

## 区域（Roi）

`lightamer-geom::Roi` 镜像 `dt_iop_roi_t`
（`src/develop/pixelpipe.h:36-39`）：整数 `x`/`y`/`width`/`height` 加浮点
`scale`。`scale == 1.0` 是全分辨率；宽或高为零是合法的空区域（模块说
「我不需要输入」就长这样）；负的宽高是错误；零、负数、非有限的缩放
是错误（定在构造器里，见 `Roi::new`）。

运算：相交、合并（最小包围）、平移、判空、
判包含（含点）、取子区域（相对坐标，越界是错误）。
两个运算量缩放必须按位相等，否则相交/合并报 `ScaleMismatch`，
包含直接报 `false`。整数运算全部 checked，溢出是 `RoiError::Overflow`。

默认 roi 对（恒等）照 `src/develop/imageop.c:108-125`；
前推的形状照 `_dev_pixelpipe_process_rec` 从链尾调 `modify_roi_in`
（`src/develop/pixelpipe_hb.c:2575`），反推的形状照
`dt_dev_pixelpipe_get_dimensions` 顺调 `modify_roi_out`（同文件 `:4026`）。

## 画面（Frame）与预算（Budget）

`lightamer-raster::Frame` = 像素缓冲（`Vec<f32>`）+ 所在区域
（`FrameExtent`，整数矩形，不带缩放——缓冲的位置不需要缩放）+
像素格式。两个可分配的浮点格式：32 位浮点四通道预乘 Alpha
（`PixelFormat::RgbaF32Premul`，RGBA 工作格式）与单通道 32 位浮点
（`PixelFormat::MonoF32`，RAW 马赛克工作格式，4 字节/像素）；
`RgbaU8`/`RgbaU16` 只是枚举里的名字，给显示用，分配不了。

访问方式：按行（`row`/`rows`/`rows_mut`，返回连续行区间，
调用方用 `split_at_mut` 切开，各写各的，互不别名）；
按子区域（`view`/`view_mut`，读/写视图，逐行借）；
整体拷贝（`copy_from`，形状或格式不对是错误）。
越界一律运行时错误（`RasterError::OutOfBounds`），编译期挡不住——
测试里 `row(8)` 对 8 行画面报 `OutOfBounds` 就是证明。
字节大小和行列数在 64 位里算，溢出或超过可寻址内存是
`RasterError::TooLarge`。

`lightamer-sysmem::Budget` 是带硬上限的预算：`acquire` 超限是
`BudgetError` 不是崩溃；`Grant` 是 RAII，drop 即归还；
`used`/`remaining` 随时可问，`Mutex` 包着，可跨线程共享。

L0 的四个 crate 互相不依赖，所以缓冲和预算的配对住在管线层：
`lightamer_pipeline::budgeted::alloc_frame` 先扣预算再分配，
分配失败时 grant 已 drop，字节自动回去。

## 模块接口（IopModule）

`lightamer-iop-traits::IopModule`，对象安全（只有 `&self` 方法，
无泛型、无关联类型），注册表可以拿 `Vec<Arc<dyn IopModule>>`
装各种各样的模块。CORE-DESIGN §1 的草图用了 `Params`/`Piece`
关联类型，那样的 trait 做不成 `dyn` 表——自动发现要的正是那张表，
所以参数改走历史模型存的 JSON 对象（`Map<String, Value>`），
提交结果改走不透明的 `CommitData = Arc<dyn Any + Send + Sync>`
（模块自己 downcast 转回）。

方法与 `src/iop/iop_api.h` 的对应：`desc` → `op`/`flags()`；
`colorspaces` → `default/input/output_colorspace`（`:97-110`，
未填的描述默认走 `(Rgb, Rgb)`——本管线的工作空间是线性 RGB，
缓冲是 RGBA；darktable 那边 `input/output` 默认回落到
`default_colorspace`，见 `src/develop/format.c:81-93`）；
`commit` → `commit_params`（`:199`）；`roi_out`/`roi_in` →
`modify_roi_out`/`modify_roi_in`（`:213-243`，默认恒等）；
`tiling` → `tiling_callback`（`:119-124`，默认见下）；
`process` → `process`；`stats` → 无上游对应（我们的声明：默认 `Local`，`WholeImage`/`Proxy` 在流式下拒绝，见「行带流式」）；`output_format` → 无上游对应（我们的声明：默认输出格式 = 输入格式，管线按它给每个节点分配输出平面）。

错误分四种（`PipeError`），每种带一句人话：
`InvalidParams`（参数不对）、`RoiMismatch`（区域对不上）、
`UnsupportedFormat`（不支持的格式）、`Backend`（后端出错）。

给模块作者的五个小工具（`params` 模块）：`get_float`/`get_int`/
`get_bool`/`get_text`/`get_floats`，从 `{"type": ..., "value": ...}`
单元里取值，找不到或类型不对报 `InvalidParams`。

接口签名只用本 crate 的类型：roi 用线形（`Roi`，`lightamer-geom::Roi`
的同形镜像，管线在边界处逐字段转换并校验）；
`process` 用借来的像素视图（`Plane`/`PlaneMut`，行访问带界检查）；
提交的图像信息（`ImageInfo`：解码尺寸 + 相机输入色彩空间 + 缓冲格式 +
RAW 事实，可选）也住这里——
L0 不许跨 crate 依赖，trait 要用的类型只能和 trait 住一起。
RAW 输入由解码 crate 的 `pipe_input` 喂入（`MonoF32` 帧 + `RawFacts`，输入空间 `Raw`）；引擎侧 `RawFileSource`（CLI）实现 `InputSource`，探尺寸只解元数据、整帧与流式共享一次像素解码。

## 几何链

`lightamer-pipeline::chain`。调用方给一串按执行顺序排好的
`PipeNode`（标识、多实例下标、参数）加一个 `ModuleLookup`
（按标识找模块；闭包和 `HashMap` 都是 lookup）。
三件事：

1. **提交**（`build_chain`）：逐个调 `commit`，找不到模块是
   `UnknownModule`，提交拒绝是 `Commit`（带模块标识和源错误）。
2. **前推**（`forward`）：从最后想要的输出区域出发，逆执行顺序，
   每个节点的输入变成上一个节点的输出，一直推到需要解码的那块。
   相邻两项恒有 `geos[i].output == geos[i+1].input`。
3. **反推**（`backward_check`）：从最前面的输入顺推回去，
   逐节点核对与前推记录一致；第一个对不上的报 `Roundtrip`。

模块返回的线形在 `from_wire` 处校验（`lightamer-geom` 的构造器），
坏区域报 `BadRoi` 并点名模块。核心里没有写死的模块标识，
测试全用 `mod_a`/`mod_sink` 这类假名
（`check-no-iop-names` 会扫这个 crate）。

## 格式协商

`lightamer-pipeline::negotiate`。每个节点报自己的
（输入空间，输出空间）；`negotiate` 顺链走一遍，相邻两节点
首尾空间不一致就在它们之间记一笔 `ColorStep { after, from, to }`。
全链同空间时零笔。这一波只出计划（`ColorPlan`），变换本身在 B5。

## 分块

请求（`lightamer-iop-traits::TilingReq`）镜像 `dt_develop_tiling_t`
（`src/develop/tiling.h:25-41`）的处理器侧：`factor`/`maxbuf`/
`overhead`/`overlap`/`align`。图形处理器那一侧的分块请求等图形处理器
那一波再加。默认值照 `default_tiling_callback`
（`src/develop/tiling.c:1903-1921`）：`factor = 1 + 输出面积/输入面积`，
`maxbuf = 1`，零开销、零重叠、对齐 1。
两处写明的偏离：空输入给 `factor = 2`（上游是除零得 `inf`）；
`TILING_FULL_ROI` 的 overlap-4 分支暂无对应（我们的标志词汇没有这一位）。

决策（`lightamer-pipeline::tiling::decide`）是纯函数：
输入（请求，输入/输出区域，一块画面的字节数，预算），
输出 `NoTiling` 或 `Tiled(TileGrid)`（块数、每块位置大小、
每块含重叠的输入区域）。算法照 `_default_process_tiling_ptp`
（`src/develop/tiling.c:571-822`）移植：

1. 吻合检查：`factor * 画面 + overhead <= 预算` 则不分块
   （`dt_tiling_piece_fits_host_memory`，`:1923-1933`）。
2. 无增益门：`factor < 2.2` 且开销小则不分块（`:599-610`）。
3. 可用 = 预算 − 输入整帧 − 输出整帧 − 开销，下限零（`:613-615`）；
   单块 = max(可用 / factor, 单块下限)（上游和 `dt_get_singlebuffer_mem()`
   取大，`:613-620`；B1-b 起 `decide` 收一个下限参数，调用方按实例给，
   见「四种管线实例」；传零即 B1-a 行为）。
4. 收缩：超单块则按 `scale` 缩（宽小于高且 `scale >= 0.333` 缩高，
   高小于等于宽且 `scale >= 0.333` 缩宽，否则两边缩 `sqrt(scale)`，
   一律 `floor`，`:629-646`；阈值是上游字面量 `0.333f`（`:634,638`），
   我方以 `0.333f32 as f64` 逐位拓宽到 `f64`——不是 `1.0 / 3.0`，
   两者在 `[0.3330000, 0.3333333)` 内走不同分支）；重叠主导
   （`3 * overlap` 超过任一边）则改方形（`:652-658`，ptp 路不贴对齐）。
5. 对齐：真切分时宽高向下贴（`:670-671`），重叠向上贴（`:674-675`）。
6. 步长 = 块 − 2*重叠（下限 1，`:678-679`）；
   块数 = `ceil(全幅 / 步长)`（`:682-683`）。
7. 超过 10000 块则放弃不分块（`:81-84` 的默认档；
   上游的 `unrestricted` 档暂无对应）。
8. 逐块：末块钳到帧内；两端都窄过 2*重叠的末块跳过（`:733`）；
   好块只裁前侧重叠（后侧由下一块覆盖写，`:780-790`）。

分发照 `:1176`（roi 按位相等才走 ptp；`TILING_FULL_ROI` 那半暂无）。
形状对不上的回答 `NoTiling`：roi 变体路（迭代拟合 `:527-567` + 单纯形
`:496-525`）要模块回调进循环，仍在后面（B1-b 只执行 ptp 网格）。

## 四种管线实例

`lightamer-pipeline::kinds`。darktable 是五种同构管线
（`dt_dev_pixelpipe_type_t`，`src/develop/pixelpipe.h:42-63`），
B1 立四种（第二个预览管线暂无对应）：
`Full`（完整分辨率）、`Export`（导出）、`Preview`（预览）、
`Thumbnail`（缩略图）。B1-a 那张常量表（`quota()`）自 B1-b 起只作上限；
活预算按物理内存推导（`quota_for(kind, total)`）：
每种取物理内存的固定分成（Full/Export 各 16%、Preview 5%、
Thumbnail 3%，合计 40%），钳进[下限，上限]（下限 Full/Export
512 MiB、Preview 256 MiB、Thumbnail 128 MiB，上限即 B1-a 表）；
四份钳完若超 40% 池（只发生在下限都放不下的小机器上），按比例压回池内。
分成照 darktable `default` 资源档（`src/common/darktable.c:2334-2339`
的 512/1024，`resourcelevel` 默认 `default`，见
`data/darktableconfig.xml.in`），收紧到 40%（16 GiB 开发机上是
6.4 GiB，看门狗 9 GB 线之下）；Thumbnail 的 3% 对应上游整管 `/3`
（`dt_get_available_pipe_mem`，`pixelpipe_hb.c:359-376`）。

16 GiB 机器上的值：Full/Export 各 2,748,779,069 B（2.56 GiB）、
Preview 858,993,459 B（0.8 GiB）、Thumbnail 515,396,075 B（0.48 GiB），
合计 6,871,947,672 B（6.4 GiB）。

单块下限（`singlebuffer_floor(kind, total)`）：Full/Export 取
max(2 MiB, 物理/128)（与上游 `default` 档的 `dt_get_singlebuffer_mem()`
逐字相同，`darktable.c:3081-3091`），Preview 取 max(2 MiB, 物理/256)、
Thumbnail 取 max(2 MiB, 物理/512)（帧小，下限逐级减半，否则单块比帧还大）。
16 GiB 上四份是 128/128/64/32 MiB。

`cache_slots` 沿用 B1-a 表（槽位 8/4/4/2）：

| 实例 | 预算上限 | 下限 | 分成 | 缓存槽位 |
|---|---|---|---|---|
| Full | 4 GiB | 512 MiB | 16% | 8 |
| Export | 4 GiB | 512 MiB | 16% | 4 |
| Preview | 1 GiB | 256 MiB | 5% | 4 |
| Thumbnail | 512 MiB | 128 MiB | 3% | 2 |

（darktable 那边 Full 缓存 64 行、Preview 12 行，计的是行不是面，
数字不可比，只借「同构不同配额」的形状。）

B1-b 的表里还有一列「单块上限」（`max_tile_bytes`，256/256/64/16 MiB），
B1-b2 删掉了：块大小已经由活预算定死（`可用 / factor` 再夹单块下限），
静态上限没有上游对应（`tiling.c` 只看可用内存），留着只会逼出
「上限低于下限时谁赢」这种自造规则。删后块大小的约束只剩两条：
预算（能分多小）与下限（最小一块）。

## 执行（B1-b，B1-b2 修）

`lightamer-pipeline::render`。`Pipe` 是一种实例一台：持有预算（`Arc<Budget>`）
和画面缓存（`PlaneCache`）。`render` 是同步调用，调用方给执行序节点、
模块来源、输入画面与图像信息、输入标识（u64，解码结果换了它就变）、
处理版本号（u32 明文，管线不依赖历史模型的类型）、想要的输出区域、
取消检查（`&dyn Fn() -> bool`）；交出输出画面（`OutputFrame`）或分了类型的
错误（`RenderError` 十种：B1-b 七种链/几何、格式缺口、节点、预算、画面、
输入、取消，加 B1-b2 的超上限，加 B1d-a 流式的两种：拒绝与落盘）。

次序照 `_dev_pixelpipe_process_rec`（`pixelpipe_hb.c:2323-2480` 的缓存优先
加 `:2575-2600` 的推区域/递归/执行），去掉没有的步骤（无解码腿、无色彩
变换、无 OpenCL/混合/蒙版/直方图）：建图并提交 → 前推几何（反推核对）→
足迹检查（见「上限」，超了在分配之前就拒）→
格式协商（有变换步骤即报 `ColorGap`，点名起止空间；变换本身在 B5）→
逐节点：查缓存（命中复用，不调 `process`、不重分配，即时 touch）→
未命中则分块决策 → 让路（见下）→
不分块：分配输出画面调一次 `process`；分块：逐块从上游画面取出含重叠的
输入调 `process`，好块写回 → 算完立刻写缓存。

写入时机（B1-b2 改）：每个节点算完立刻 `insert`，不再攒到结尾。
峰值从「链长 × 整帧」变成「缓存 + 正在用的输入 + 新输出」：
6100 万像素五节点在 2.56 GiB 预算上从超预算报错变成成功（见 B1-b2 报告）。
取消或出错时，已经算完的节点的画面留在缓存里——键是由内容决定的
（上游全部节点的参数、几何、输入标识、处理版本号），这些画面完整有效，
下一次渲染正好能用；要保证的只有一条：没有半截的画面进缓存
（分块中途取消同理：没算完的节点一个条目不留）。

让路规则（B1-b2 新）：分配一块新画面（节点输出、分块暂存、空链拷贝）
被预算拒绝时，把缓存里「本次渲染没有命中」的条目按最久没用逐个淘汰，
淘汰到放得下为止；本次命中的条目是活输入，永不让路；淘汰光了还不够，
才是预算不够的错误（临时的画面随栈帧放掉，预算全数归还）。
上游同款：`_get_oldest_cacheline`/`_get_cacheline`
（`pixelpipe_cache.c:208-255`）取最旧行复用。

上限（B1-b2 新）：一个节点运行时输入和输出两帧必须同时在，
所以每种实例有一个能处理的最大帧。公式（`Pipe::max_frame_bytes`）：
最大帧字节数 =（预算 − 2 × 单块下限）÷ 2。依据：两帧同在是硬约束；
`2 × 单块下限` 是分块暂存对在最小块下的余量。执行时用的是更精的
逐节点形：节点 0 需 输出 + 2 × 下限 ≤ 预算（它的输入是调用方的画面，
不占预算），其余节点需 输入 + 输出 + 2 × 下限 ≤ 预算；任一节点超了，
`FrameTooLarge` 点名节点下标、要多少字节、预算多少字节，在跑之前就拒，
预算和缓存原样。两句诚实话：块大于下限时暂存对超余量，分块节点仍可能
中途报预算不够（分了类型，不崩）；保证只对闲管成立——调用方手里还攥着
的输出不参与淘汰，攥满了再渲照样报预算不够（有测试钉住）。

16 GiB 机器上的上限表（预算与下限见上）：

| 实例 | 最大帧（字节） | 最大帧（像素） | 6100 万像素 |
|---|---|---|---|
| Full | 1,240,171,806 | 77,510,737 | 放得下（占 77.7%） |
| Export | 1,240,171,806 | 77,510,737 | 放得下（占 77.7%） |
| Preview | 362,387,865 | 22,649,241 | 放不下（预览只接小图） |
| Thumbnail | 224,143,605 | 14,008,975 | 放不下（缩略图只接小图） |

单通道（`MonoF32`，4 字节/像素）同表字节上限换算像素：Full/Export 各
310,042,951 像素（一帧 A7R5 马赛克 9568×6376 = 61,005,568 像素 =
244,022,272 B，占 Full 上限 19.7%）、Preview 90,596,966 像素、Thumbnail
56,035,901 像素。预算、占用检查、缓存记账一律按每块平面自己的格式算。

分块执行照 `_default_process_tiling_ptp`（`tiling.c:690-806`）：一对可复用的
输入/输出暂存（按最大块分配，充电到预算上，分配前先让路）；每块绝对坐标的
`iroi`/`oroi`（`:740-741`）；只把好块（裁掉前侧重叠）拷回（`:780-790`）。帧边截掉的
重叠由网格 builder 钳掉（B1-a 已定），执行侧按 `view` containment 拷贝。
与上游的两处偏离：块与块之间串行（块级并行不做）；暂存分配失败是分了类型
的预算错误（上游回落不分块加一条日志，我方确定性优先）。

缓存键（`cache::chain_keys`）是链式的 FNV-1a：域名标签 +
实例种类 ＋ 输入标识 ＋ 处理版本号 ＋ 逐节点（链位置、模块标识、多实例
下标、参数规范 JSON、输入/输出区域，缩放按位）。算法与历史模型的 `hash64`
同为 FNV-1a（`settings.rs:492`），在这个 crate 里另算一份，不添依赖；
标准向量（空串、`foobar`）钉死。形状照上游 `_dev_pixelpipe_cache_basichash`
加区域折叠（`pixelpipe_cache.c:99-184`：图像 id、管线类型、逐 piece 的
`piece->hash` 即操作名＋实例＋参数 `imageop.c:2562-2595`）。同样的请求第二
次零 `process`；改一个参数只重算它及下游（上游键不变）；实例、处理版本号、
输入标识任一不同即互不命中。成功收尾时按上游优先的顺序 touch
（B1-b 规则：下游改参数复用上游，反之不成立）。

预算跟着画面走：每幅画面配一份 `SharedGrant`（`sysmem` 新增的 `Arc` 授权；
借用式 `Grant` 原样保留），画面包在 `Arc<SharedFrame>` 里，缓存条目和返回
的输出各持一份，**最后一个持有者放手预算才回来**，不靠调用者守纪律。
缓存按字节与槽位双重准入（字节上限 = 预算的一半，给下一趟的工作集留地方），
淘汰按最久没用；放不下的平面跳过缓存，渲染照常成功。取消与出错保留已完成
节点的画面（见「写入时机」），临时的画面随栈帧放掉，预算全数归还。

取消在每个节点前、每块前各查一次；已置的取消在入口即拦。空输入区域的节点
照常调 `process`（输入是空平面）。空链是拷贝（输入须已在想要的区域，
分配前同样先让路；空链不过足迹预检——无节点下标可点名——超预算大帧走
`OutOfBudget`，同样分类型、全归还）。

按行并行（`lightamer-iop-traits::parallel::par_map_rows`，rayon）：给模块作者
的小工具，按行切块并行跑闭包，写面天然不交叠，与串行逐位相同。恒等模块用
它来抄；分块之间串行。

## 渲染作业（引擎这一侧，B1-c）

管线只给同步的 `Pipe::render`；接到引擎之后，渲染走作业
（`lightamer-engine/src/render.rs`，L4 依赖 L2，分层检查放行，
反方向不许）。引擎自己建四种实例的管线各一台，预算按物理内存
（读不到时按 8 GiB 保守值）；每台管线包一把锁，同一种实例的两个
作业不能同时渲染，不同实例互不阻塞。

**注入口**（由嵌入引擎的一方注入，引擎自己不去找），两个都是 trait，
默认都没有：

- **输入来源**（`InputSource`）：给照片标识，交出画面、图像信息和输入
  标识，或分了类型的错误。只在作业线程里调（将来是解码，可能很慢）。
  没有它时 `render.request` 报分了类型的错误，不起作业。
- **模块来源**（`ModuleSource`）：按标识找模块。没有它、或标识找不到
  时，那些实例跳过（记进本次记录），链短或空，输出等于输入。

核心里没有模块标识的中心名单：执行序按注册表的非 raw 默认链排，
注册表里没有的标识排在后面、按（标识，多实例下标）排序；B1 没有
解码、没有照片的 raw 信号，所以先全走非 raw 链，B2 再按照片分流。

**两条命令**（经 `execute` 登记，参数 `photo` + `kind`，`kind` 是
`full`/`export`/`preview`/`thumbnail` 四词之一）：

- `render.request`：快照请求那一刻的当前设置（渲染中途再改参数不影响
  这一代），把该（照片，实例）的代号加一，取代在飞的那一代（置它的
  取消标志——就是传给管线的取消检查），起一个作业，**立即返回**
  `{"generation", "job"}`。
- `render.cancel`：取消在飞的那一代，不起新的；没有在飞时成功返回
  `{"cancelled": false}`（幂等：和完成撞车不报错）。

**作业**在池线程里跑：排序跳过（禁用的、找不到模块的记 `skipped`）→
取输入（锁外，慢解码不挡管线）→ 抱住该实例的锁调 `Pipe::render`（锁内
先查一次取消）→ 把像素拷出来发回。画面和记录经作业消息回到引擎线程
（`collect` 那条路，和恢复作业同款），作业线程不碰引擎的状态。
被取代的作业在下一次取消检查处让出：节点之间、块之间各查一次，
最坏多占一把锁一个 `process` 调用的时长。

**结果的保留与事件**：引擎为每对（照片，实例）保留最新一代完成的画面
（拷出预算之外，不占管线预算）和它那次的记录，直到被新一代取代或会话
关闭（B1d-b 起按字节上限淘汰最久没用的，见「行带流式（B1d-b，引擎这一侧）」）；
读法是方法（`rendered_image` / `last_render_record`），不是命令。
`RenderReady { photo, kind, generation }` 只为最新一代发；最新一代失败
时 `RenderFailed { photo, kind, generation, reason }`；被取代或取消的那
一代不发渲染事件（作业通用的开始/进度/结束事件照常）。

**每次渲染的记录**：管线侧 `Pipe::last_trace()` 给出上次渲染每个节点的
`NodeReport { id, multi, hit, process_calls, millis }`（命中零调用零毫秒；
未命中按块数计调用、实测毫秒；取消或失败留已完成的前缀，空链留空），
引擎把它连同 `skipped` 一起收进 `RenderRecord`。渲染不写库。

## 行带流式（B1d-a，管线这一侧）

`lightamer-pipeline::stream`。`Pipe::render_stream` 与 `render` 收同样的请求
（`RenderRequest`），外加一个接收者：每算完一条带或一个方块，就把它的位置、
大小和画面交给接收者。`render` 一个字没动。流式这一趟没有整帧足迹预检——
超限的图来流式就是因为整帧放不下；但每一步分配（带和方块的缓冲、交接收者的
那块画面）照旧走预算，放不下是分了类型的 `OutOfBudget`。上限仍由资源定，
不设固定的像素上限。

两种模式照 Lumen RAW（`lumen/large_image.py`，MIT，见 `NOTICE`）：

- **条带**：链上每个模块的影响范围（分块请求里的 `overlap`）都是零，并且
  不改几何 → 整宽的带，每带 64 行（`STRIP_ROWS`，上游 `:10`），最后一条取余数。
- **方块**：有任何一个大于零 → 方块。余量 = 链上各模块 `overlap` 的和；
  边长 = `sqrt(预算 × 0.25 ÷ 每像素字节数) − 2 × 余量`，钳在 512 到 8192 之间
  （上游 `block_size`，`:143-148`）。「预算」是本实例的预算（不是探测到的可用
  内存，规划才可复现）；「每像素字节数」是 150（初值照上游取 100，上游
  `FRAME_BYTES` 在 61 MP 上实测 55–76 取整 100，`:134-136`；B1d-b 校准：
  三轮块模式探针在合成模糊链上量到边际常驻 145/144/158 字节每输入像素、
  过原点的直线，150 取整落在带内；真模块带着自己的暂存来，到时再量）。

余量没有上游那 4 像素的富余（上游 `spatial_margin` 在非零余量上加 4，
`lumen/engine.py:922`）：上游的余量是每个工具的手估公式，加 4 是盖估计误差；
我们的余量是模块声明的 `overlap`，另有一致性测试看着（见下），自加富余只会
把块切小。余量再大也不拒绝：放大饱和后钳到帧，只是整帧都读；不设「影响范围
不超过多少」的门槛。

规划器（`plan_stream`）是纯函数：输入几何链、各模块的影响范围、预算、帧尺寸、
每像素字节数；输出模式、带或方块的列表、每一块要读的输入区。每一带、每一块
要读的输入区 = 输出区沿几何链反推（`forward` 现成）→ 与输出区取并 → 按余量
向外放大 → 钳到帧内。

执行逐带或逐块：查取消 → 取输入区（整帧输入画面里裁；链头说「我不需要输入」
时不取，第一节点拿空平面）→ 跑完整条链（一对复用的工作画面里倒）→ 把属于
这一带或这一块的那部分裁出来交给接收者。每一带、每一块之前查一次取消；
取消或出错时工作画面随栈帧放掉，预算全数归还。空链是逐带拷贝；只有一个节点、
头节点无输入都有测试钉住。流式这一趟不碰缓存（不读不写）：调研（§3.7）说
「不写、读可以」，我们连读也免了——流式轮意味着整帧放不下，整帧的缓存条目
不可能存在，读命中只会发生在「先整帧后流式」的测试里，反而盖住流式自己的路。

输出的拼装（`StreamSink`，可选的助手）：调用方在跑之前备好——输出 ≤ 内存阈值
进内存，超了落成内存映射的临时文件（上游 `allocate`，`:23-36`；匿名文件，
drop 即删，取消和出错也不留）。落盘字节数受调用方传进来的上限约束，超了在跑
之前就分类型拒绝。文件目录调用方可指定，不指定走系统临时目录。

拒绝（`StreamRefused`，都在任何分配之前，预算和缓存原样）：会改几何的模块
（两档中心探针 + 整帧几何核对：输入增长随区域变、或输入盖不住输出，即拒）；
声明「必须看整图」的；声明「看代理图」的（代理统计随第一个要它的模块做）；
`overlap` 与自己 `roi_in` 自相矛盾的（`OverlapMismatch`）。

模块接口多一条声明（`IopModule::stats`，默认 `Local`，现有模块零改动）：
`Local`（只看自己周围）、`WholeImage`（必须看整图）、
`Proxy { max_long_edge }`（可看缩小代理图）。另有一条一致性判据
（`check_overlap_covers`）：模块声称的 `overlap` 必须盖住它自己 `roi_in` 报的
增长，四边缺一边即错；它只对声明不对 `process`——`process` 里偷读块外像素的
撒谎，由整帧对流式的逐位测试拦（有测试钉住：声称零重叠的模糊在条带边界出缝）。

逐位相同：每一带、每一块都是把输入区按余量放大后跑完整条链，只交出属于自己的
那部分（上游 `process_region`，`lumen/engine.py:1342`），所以和整帧逐字节相等。
三例钉住：条带（恒等 + 增益）、方块（含重叠 8 的模糊）、混合链；另有双跑逐位、
200 MP 默认不跑的计时（条带门 1 GB，方块另报数）。

## 行带流式（B1d-b，引擎这一侧）

**区域输入**（`InputSource::fetch_region`，默认 = 整帧加裁剪，B1-c 行为逐位不变；
大帧的来源自己按块算，不走默认）。**超限自动转**：完整分辨率和导出两种实例上，
作业先探尺寸（`InputSource::probe`，只拿图像信息和整幅尺寸，不取像素），探到的
整幅超过管线交出的最大帧（`Pipe::max_frame_bytes`）就直接走流式：一次
`render_stream_from`，管线规划一次、逐块经来源取输入区，结果拼进 `StreamSink`；
流式这条路一次都不整帧取输入。放得下才整帧取输入、跑整帧入口（B1-c 原样）；
整帧入口报「这帧在这根管子上跑不了」时（只剩链上各节点尺寸不一致的形状），
作业丢掉整帧输入再走流式。预览和缩略图实例不转，照旧报错。代号取代、取消、
事件规则不变：只有最新一代落地，被取代的在块与块之间让出。流式自己的拒绝
（会改几何的模块、要看整图的模块）原样透出，不退回。

**引擎配置**（`EngineConfig`，设置面板那一波再给界面）：落盘字节上限（默认 8 GiB，
超了在跑之前就分类型拒绝）、落盘目录（不指定走系统临时目录；引擎只传位置和上限，
临时文件的建和删都在管线那一侧）、保留字节上限（默认 1 GiB）、拼装内存阈值
（默认 256 MiB，Lumen `MAP_BYTES` 同值：以下进内存，以上落内存映射文件）。

**结果的保留**（B1-c 的无上限缺口在此关掉）：每对（照片，实例）保留的渲染结果按
字节计（内存按实际向量长、映射按文件长，不再按宽×高×16 估算），超上限时最久没用的先淘汰；读一次算用一次；
调用方还握着的（克隆走的画面，映射文件共享持有）不回收，文件随最后一个持有者走；
缩略图实例的结果不进这条保留路径（以后归缩略图缓存），它的记录照常记、事件照常发。
单张超过上限的图：正常交付（事件照发），只是一落地就因超限不保留。

**拒绝的透出**：输入放不进内存（来源拒收）、落盘超上限、预算不够、流式被拒——
四个都在引擎这一层原样透出，分了类型、一句人能读的话，不包装成笼统的失败。
上限仍由资源定，不设固定的像素上限。

## 行带流式（B1d-c，探尺寸直流）

B1d-b 的引擎路先整帧取输入再试整帧入口，流式峰值跟着帧的大小涨（200MP 条带
4.58GB，管线自己的同图测试只要 66MB）。本节修掉它：

**管线**：`StreamInput`（给一块区域，交出那一块的画面）+ `StreamRequest`
（`RenderRequest` 去掉整帧画面）+ `Pipe::render_stream_from`（请求里不带画面，
带来源；管线规划一次，逐块取输入、跑完整条链、交接收者）。`render_stream`
保留，改经此入口实现（来源 = 整帧裁一块）；`render` 一个字没动。

**引擎**：`InputSource::probe`（默认 = 整帧取出来、只留下信息；大帧来源自己
便宜地答，否则整帧路付两次解码）。作业次序：能转流式的作业（完整/导出 +
非空链）先探尺寸 → 该转就直流 → 否则整帧；预览/缩略图/空链不探，整帧路只
取一次输入；来源必须保证探到的尺寸与真实像素一致（探大按区域取越界是
分类型失败，探小输出偏小）。B1d-b 那套引擎自己规划、逐块嵌套 `render_stream`
的循环删掉（规划只在管线里做一次）。上限表重测后，条带峰值是几十 MB 加
拼装缓冲，方块在 1GB 以内，直到撞磁盘上限
（见 `B1dc-REPORT.md` 新旧表并排）。
