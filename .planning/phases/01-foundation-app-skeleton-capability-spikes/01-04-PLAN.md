# Plan 04 — IOPModule protocol + V50Order + pixelpipe skeleton (success criterion #3: no-op pixelpipe runs through EditorMTKView)

## Goal

Port the Darktable iop module contract and module ordering into Swift, and prove the contract compiles + runs end-to-end as a no-op pixelpipe:
1. `IOPModule` Swift protocol (FOUND-03): `associatedtype Params: Codable, Hashable`; `process`/`modifyROIOut`/`modifyROIIn`/`commitParams`/`reloadDefaults`; static `opName`, `iopOrder`, `flags`, `defaultColorspace`. Faithful port of `iop_api.h`.
2. `V50Order` (`Sources/IOP/iop_order.swift`): the `v50_order` table ported verbatim from `darktable/src/common/iop_order.c:298-415` (planner's source read confirms the table — the 28.5 cluster with 6 modules is preserved). This is the single source of truth for module ordering that Phase 2 history + every Phase 3+ iop references.
3. Supporting types: `IOPFlags: OptionSet`, `IOPColorspace` enum, `ROI` struct, `IOPiece` struct (per-piece pipe state), `IOPBufferDesc`.
4. `PassthroughModule: IOPModule` — the no-op conformance that proves the protocol works (success criterion #3).
5. `PixelPipe` skeleton — runs an ordered list of `IOPModule` pieces through `MetalContext.dispatch2D`. Phase 1 runs a single `PassthroughModule` piece; the recursive cache + multi-resolution arrives in Phase 2.
6. Wire the no-op pixelpipe into the editor: `EditorState` runs the decoded RAW through `PixelPipe([PassthroughModule()])` → output texture → `EditorMTKView`. After this plan, the displayed image flows through the iop contract (not just a raw CIImage blit), proving the architecture that Phase 2+ plugs into.

This plan satisfies Phase 1 success criterion #3: "The IOPModule protocol and v50_order order table compile, and a no-op pixelpipe chain (single pass-through piece) runs without error through the EditorMTKView NSViewRepresentable bridge."

## Tracer vertebra mapping

Plans 01-03 delivered "open RAW → display pixels." This plan inserts the iop contract *between* decode and display: the decoded CIImage now flows through `PixelPipe([PassthroughModule()])` before reaching the viewport. The vertebra is unchanged from the user's perspective (same pixels), but the architecture is now the one Phase 2+ builds on — every future iop is a piece in this pipe.

## Must-haves (goal-backward verification)

- [ ] `IOPModule` protocol compiles with `associatedtype Params: Codable, Hashable` (FOUND-03).
- [ ] `V50Order.entries` contains every opName from `darktable/src/common/iop_order.c:298-415`, ported verbatim.
- [ ] The 28.5 cluster is intact: exactly 6 entries at order 28.5 (`channelmixerrgb`, `diffuse`, `censorize`, `negadoctor`, `blurs`, `primaries`).
- [ ] Every opName in `V50Order.entries` is unique (no duplicate opNames; only order values deliberately collide).
- [ ] `PassthroughModule` conforms to `IOPModule` and its `Params` is `Codable & Hashable`.
- [ ] `PixelPipe.run(input:)` executes a `[PassthroughModule()]` chain through `MetalContext.dispatch2D` without error.
- [ ] The displayed image (after this plan) flows through the pixelpipe, not a direct CIImage blit — verified by temporarily swapping `PassthroughModule` for a no-op and confirming the image still renders (success criterion #3).
- [ ] All types compile under Swift 6 strict concurrency; `IOPiece` is a value type (Sendable).

## Reversibility gates

- **D-25 (AppError) — COSTLY (cross-layer contract).** Already locked in Plan 01; the `IOPModule.process` `throws` path routes through it. No new checkpoint needed (Plan 01's checkpoint covers it), but this plan is the first heavy consumer — affirm the error flow.
- No NEW one-way decisions in this plan. The `IOPModule` protocol shape is costly to change but is a faithful port of a stable external contract (`iop_api.h`), so its reversibility is bounded by Darktable's own API stability. The `v50_order` table is verbatim port — reversing it means diverging from Darktable, which CONTEXT.md locks against.

**read_first:**

- `/Volumes/UNITEK/Documents/Development/darktable/src/common/iop_order.c:298-415` — the v50_order table (source of truth)

**decision:** Lock the iop contract before writing `IOPModule.swift`:
1. **FOUND-03 protocol:** `protocol IOPModule { associatedtype Params: Codable, Hashable; static var opName: String; static var iopOrder: Float; static var flags: IOPFlags; static var defaultColorspace: IOPColorspace; func reloadDefaults(image:) async -> Params; func commitParams(_:into:) async; func modifyROIOut(_:input:piece:); func modifyROIIn(output:_:piece:); func process(input:output:roiIn:roiOut:piece:metal:) async throws }`. The `associatedtype` means the pixelpipe uses generics or a type-erased `AnyIOPModule` wrapper (Phase 2 ModuleRegistry). For Phase 1, `PixelPipe` is generic over a single concrete module type or uses a protocol-with-association-erased array.
2. **v50_order verbatim port:** `V50Order.entries: [(opName: String, order: Float)]` is byte-for-byte from `iop_order.c:298-415`, including out-of-source-order entries (e.g. `lut3d` at 36.0 appears physically between `filmicrgb` 46.0 and `colisa` 47.0 in the source — port in source order, the `order` field carries the semantic position). The 28.5 cluster (6 modules) is preserved.
3. **Params = Codable & Hashable struct** (FOUND-03 mandatory). No classes for params. Auto-synthesized conformance.
4. **`defaultColorspace` mandatory** (iop_api.h:97 REQUIRED). Phase 1's PassthroughModule uses `.RGB`; the terminal trio (colorin/colorout/gamma) is Phase 2.
5. **Phase 1 scope:** `PixelPipe` runs a flat ordered list of pieces — NO recursive cache, NO multi-resolution, NO ROI negotiation beyond identity. Those are Phase 2. The Phase 1 pipe is a straight-line `for module in modules { module.process(...) }`.

**acceptance_criteria:**
- Checkpoint task marked done before 01-04-02.
- The five locked decisions affirmed (FOUND-03 + CONTEXT.md record the user sign-off).

## Task 01-04-05 — `PixelPipe` skeleton (flat ordered module list, no cache, runs through MetalContext)

**read_first:**
- `.planning/phases/01-foundation-app-skeleton-capability-spikes/01-RESEARCH.md` — §5 (the pixelpipe discussion; Phase 1 = flat list, Phase 2 = recursive cache)
- `/Volumes/UNITEK/Documents/Development/darktable/src/develop/pixelpipe_hb.c:1838-1925` — `_dev_pixelpipe_process_rec` recursive core (reference for Phase 2; Phase 1 is the non-recursive precursor)
- `Sources/IOP/IOPModule.swift`, `Sources/IOP/Passthrough.swift` (this plan)
- `Sources/Core/MetalContext.swift` (Plan 03)

**action:** Create `Sources/IOP/PixelPipe.swift` defining the Phase 1 skeleton pipe. Because `IOPModule` has an `associatedtype`, a heterogeneous `[any IOPModule]` array is not directly possible. Two options — pick the simpler for Phase 1:
- **Option A (recommended):** Define `public struct AnyIOPModule: IOPModule` type-erased wrapper using generics-closure erasure (`init<M: IOPModule>(_ module: M)` storing `process` etc. as closures). Then `PixelPipe` holds `[AnyIOPModule]`. This is the Phase 2 `ModuleRegistry` foundation.
- **Option B:** `PixelPipe` is generic `PixelPipe<M: IOPModule>` over a single module type — too restrictive for Phase 2 (mixed module types).

Use **Option A.** Create:
1. `public struct AnyIOPModule: IOPModule` — type-erased wrapper. `public init<M: IOPModule>(_ module: M)` erases the module. `Params` = `AnyParams` (a type-erased Codable+Hashable box) or, simpler for Phase 1, the wrapper re-exposes the protocol via closures and `Params` is `NoParams` (an empty concrete type). The Phase 1 pipe only needs to call `process`, so the wrapper stores a `process: (MTLBuffer, MTLBuffer, ROI, ROI, IOPiece, MetalContext) async throws -> Void` closure captured from the underlying module.
2. `public final class PixelPipe` (or `actor` if mutable state is added; Phase 1 has none so `struct`/`final class` is fine — make it `final class` for reference semantics the EditorState can hold): holds `var modules: [AnyIOPModule]` (sorted by `iopOrder` on init) and `func run(input: MTLBuffer, roi: ROI, metal: MetalContext) async throws -> MTLBuffer` — allocates an output buffer matching input size, then for each module: call `module.modifyROIOut`/`modifyROIIn` (identity for PassthroughModule), call `module.process(input:output:...)` where output becomes the next input. For a single-module pipe this is one `process` call. Return the final buffer.
3. For Phase 1 the pipe operates on `MTLBuffer` (float4 per pixel, `roi.width * roi.height` elements). The texture-to-buffer staging (CIImage → texture via Plan 03's CIContextPool, then texture → buffer for the pipe, then buffer → texture for display) is a Phase 1 simplification — Phase 2 will operate on textures throughout. Document this simplification in a comment.

Phase 1 deliberately omits: recursive `processRec`, per-module per-ROI cache, hash-hit fast path, multi-resolution (FULL/PREVIEW/THUMBNAIL/EXPORT), tiling. All Phase 2.

**acceptance_criteria:**
- `Sources/IOP/PixelPipe.swift` contains `public struct AnyIOPModule` (or equivalent type-erased wrapper) and `public final class PixelPipe`.
- `PixelPipe.run(input:roi:metal:) async throws -> MTLBuffer` exists.
- A `PixelPipe(modules: [AnyIOPModule(PassthroughModule())])` can be constructed and `run` produces an output buffer equal in size to the input.
- For a bit-exact input buffer, the output buffer equals the input (because PassthroughModule uses the bit-exact `pass_through_buffer` kernel) — verified in Plan 06's `IOPModuleTests`.
- Compiles under Swift 6 strict concurrency.
