# REPORT: gpui 原型「滚动后拖滑杆不上屏」定位——触发点是探针采样，不是 gpui

日期 2026-11-25 · 仓内 HEAD `6fbc6a885578d99e8f61b9ff5b1301a47e6583f7` · 原型/最小程序在仓外 `/Volumes/UNITEK/Documents/Development/Lightamer-gpui-spike` · 产品树零改动 · 前端 `gpui-kit 0.11.0`（`gpui-pre 0.3.14`）

## 0. Verdict

| 问题 | 结论 |
|---|---|
| 触发点是什么 | **探针的空间采样，不是应用写法**。`measure/FrameProbe.swift` 把整窗降成 **80×45 个点样本**（每格只取中心 1 像素，`FrameProbe.swift:62-63,93-101`）。1440×816 窗口上样本行距 = **18.13 px**；原型滑杆的填充条只有 **7 px**、三角标 **8 px**。偏移 602 时 module 11 的 track 落在 y=174.5，条/三角占 176.5–184.5，最近的样本行是 **172.27 / 190.40**——整条落在两行之间的 6.4 px 空隙里，一个样本都打不到。 |
| 属于哪一类写法 | **测量口径类**：用「小于采样间距的图元 + 全窗点采样」判「有没有上屏」。同一份像素，改用 480×400 采样就全部可见（§3 同一 run 双口径）。gpui 侧无任何抑制层参与（`gpui-pre` 无 scroll layer；paint 正常执行、坐标正确）。 |
| 修后数字 | 同一二进制（无代码改动）双口径：**定时器 38/40**（稀疏与密集同值）、**拖动 26/40 变化帧**（密集；稀疏 2/40），拖动事件实际送达 29/40，事件→首帧延迟中位 **4.9 ms**。最小程序对照（同一 run 双口径）：**密集 40/40 vs 稀疏 0/40**。 |
| 置信度 | **高**。三类独立证据：①同一 run 内双网格同帧打分（§3）；②同一代码只改图元高度 7px→20px，稀疏探针 0→40；③拖动中 12 张实拍截图，滑杆带区连续 5 帧变化（1.5k–6.9k 设备像素/帧）。 |
| 前几轮结论 | **作废**（塔台已宣）：不存在「滚动子树绘制被抑制」。E1 拖动的 0–1 帧可复现（我们测得 2），但它是探针分辨率下限；E2 定时器旧报的 0 帧本轮**不复现**（同一动作稀疏探针 38/40）。 |

一句话：**原型在偏移 602 下拖滑杆一直是跟手的；「0 到 1 帧」是 80×45 点采样看不见 7 px 条的必然结果。**

## 2. 机制

1. **探针只采点，不采面积。** `FrameProbe.swift:93-101`：`sy = gy*h/45 + h/90`、`sx = gx*w/80 + w/160`，每格 1 像素。816 高 → 行距 18.13 px、首行中心 9.07 px。任何高度 < 行距、且纵向落位不巧的图元都可能整条落在两行之间。
2. **原型 dt 滑杆的可见高度正好在这个量级。** `src-copy/main.rs` `slider_row()` 的 Canvas 臂：canvas 高 12 px，track 7 px（`b.origin.y+3..+10`），三角 8 px（`y+2..y+8`）。偏移 602 时该 canvas 的 `origin.y=174.5`（`CANVAS_PAINT ... y=174.5`），即条 177.5–184.5、三角 176.5–182.5；样本行 172.27 / 190.40 → **无样本命中**。
3. **「偏移 0 正常」是同一枚硬币的另一面。** 偏移 0 的拖动打在 module 1，canvas y=238.5，条 241.5–248.5；样本行 `gy=13` = 244.8 → 命中一条样本行 → 三角横向移动时依次跨过样本列，得到 13–14 帧。**同一份代码，换一行 y 就从 14 变 1**，与滚动无关，与行在采样格上的落位有关。
4. **最小程序把这条因果钉死。** 同一 run、同一帧序列，480×400 记 40 帧变化，80×45 记 0 帧（§3 第一行）；把条加高到 20 px，稀疏探针立刻 40。实拍截图（`traces/bisect/crop-E2-pre/post.png`）显示两帧之间滑杆带区 8,114 设备像素变化，填充从 15 px 画到 300 px。
5. **gpui 侧核查。** `gpui-pre-0.3.14/src/elements/div.rs:2066` prepaint 用 `with_element_offset(scroll_offset)` 平移子树、`:2609` paint 记录 bounds 与 content mask；`src/window.rs:5112` `paint_quad` 直接按记录 bounds 落 scene。没有按 scroll 状态丢弃图元的路径；`gpui-fast` 的 scroll layer 不参与（默认 pre 后端，且其 `active()` 在拖动时整体旁路）。旧报告 §2.3 的 wgpu `get_current_texture` 候选与本现象无关：像素确实上屏了。

## 3. 修前修后对照（两个口径）

同一 run 内双网格（`measure/frameprobe-dual`，480×400 与 80×45 同时打分；判据不变 `cells>=1 && maxd>=10`）。「匹配」= 事件的下一帧落在本事件与下一事件之间。

| 场景 | 密集 480×400 变化帧 | 稀疏 80×45 变化帧 | 事件匹配（密集） | 事件→首帧中位（密集） | 送达事件 |
|---|---|---|---|---|---|
| 原型 拖动 @602 | **26 / 40** | **2 / 40** | 26/40（送达者 26/29） | **4.9 ms** | 29/40 |
| 原型 拖动 @0 | **25 / 40** | **14 / 40** | 25/40（25/28） | 4.1 ms | 28/40 |
| 原型 定时器 @602 | **38 / 40** | **38 / 40** | — | — | — |
| 原型 43×scroll | 38 / 43 | 38 / 43 | — | — | — |
| 最小 E2 @600（7 px dt 条） | **40 / 40** | **0 / 40** | 37/40 | −0.8 ms | 定时器 |
| 最小 M1 @600（div 宽） | 40 / 40 | 37 / 40 | 37/40 | −0.3 ms | 定时器 |

读法：

- **偏移 602 与 0 在密集口径下同值**（26 vs 25），不存在「滚过就不上屏」。差异全部在稀疏口径（2 vs 14），且差异来自 module 11 与 module 1 的 y 落位，不是偏移。
- 拖动达不到 30/40 的物理原因：40 步 × 8 ms = 320 ms，60 Hz 下步进窗口内最多 ~19 个帧槽；本次窗口含 0.25 s 尾段共 0.64 s（38 槽），实测 26 帧 = 帧率上限的 68%，其余损失是 macOS 把 40 个合成拖动合并成 29 个送达事件。**不是应用丢帧。**
- 定时器 38/40 = 95%，已达 60 Hz 采样上限（40 tick × 16 ms 与 60 Hz 帧格互质，个别 tick 落在同一帧）。

## 4. 对 #27 的含义

- **在 gpui 上写 dt 式滑杆不需要规避任何东西。** 7 px 填充 + 8 px 三角 + canvas + `overflow_y_scroll` + 非零偏移 + 按住拖动，实拍与密集探针都证明实时跟手（4.9 ms 中位、26 帧/0.64 s）。
- **必须避免的是用「全窗 80×45 点采样」去判小图元的重绘**。判据（`cells>=1 && maxd>=10`）可以不动，但采样必须满足：样本间距 ≤ 被试图元最短边的一半，或直接做 ROI 差分。对 1440×816 全窗，等效网格 ≥ 320×180 才稳；本轮用 480×400。
- 反向也成立：**图元高度 < 采样行距时，同一份正确代码会在不同滚动偏移给出 0 或 40 两种答案**——这种指标不能用来做选型/回归门。
- 拖动响应的事件侧事实：8 ms 合成步长下 macOS 只送达 29/40；真实鼠标/触控板 60–125 Hz 报告率下会更少。这是平台事件合并，不是 gpui；若要「每步都可见」，测量动作的步长应 ≥ 16 ms。
- 旧报告里「E2 定时器 0 帧」本轮不复现（稀疏 38/40）。差异原因未定位（最可能是当时 ticker 未启动——原型 ticker 需要 `space` 键触发，`src/main.rs:756`；FAST 报告 §6.4 亦记录过 `space` 不到达的情况）。E2 的旧数字不应再引用。

## 6. 未验项

1. **未改任何产品代码**——因为没有可改的重绘缺陷；若塔台要求「稀疏探针下也 ≥30/40」，唯一途径是把 7 px 条/8 px 三角放大到 ≥19 px，这与 dt 外观冲突，本轮不做。
2. 拖动 26/40 未达 30/40：受 60 Hz 帧槽（0.64 s ≈ 38 槽）与事件合并（29/40 送达）双重限制；把步长改为 16 ms 可再测，但会偏离「沿用前几轮动作序列」。
3. 只测了 1440×816 与 600×600 两种窗口；采样混叠是窗口尺寸/行落位的函数，其他尺寸需按 §4 的间距规则重算。
4. 未测真实鼠标/触控板与不同刷新率显示器（120 Hz 下帧槽翻倍，拖动能到 ~38/40 但事件合并仍在）。
5. 未在 `gpui-fast` 后端复测（默认 pre 已足够定性；fast 的 scroll layer 在拖动期间旁路，与本题无关）。
6. E2 旧「0 帧」与本轮 38 帧的差异根因未坐实（怀疑 ticker 未启动），只登记现象。
