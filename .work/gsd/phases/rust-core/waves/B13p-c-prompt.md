## 时间花在哪（塔台读代码看到的，每一条你自己量过再认）

粘贴一万张时，每张照片经过这些：

- 引擎那边：查两次库（按标识找照片、读出整段历史），再把这段历史的每一步的 JSON 都解析一遍，重建出栈——哪怕这张照片只有一步。一万张就是两万次查询、一万次重建。缓存只装得下 64 个，所以一万张全是「没加载过」的。
- 库那边每推一步：六条语句，每条都是现写现准备的（没有复用准备好的语句）；不管有没有重做的那一段，都先执行一次「删掉游标之后的步」；同一份快照的内容，被查了一万次。
- 机械盘上，每一次碰盘都比固态盘贵一个量级。

## 要做的

**0. 先量，再动手。** 在机械盘上和内置盘上各量一遍一万张粘贴，把时间拆成三段：**读**（引擎把需要的东西从库里取出来）、**算**（算出新的设置、序列化、算键）、**写**（事务里的全部，到提交返回）。把两块盘上拆开的数写进报告。这是你动手前的底数，也是之后判断改没改对的尺子。拆数的办法你定（临时加计时也行），但报告里的数必须是从发行版构建上量出来的。

**1. 同步档。** `apply_pragmas` 里把同步档从 `NORMAL` 改成 `FULL`。测试钉住打开的库里这个值就是 `FULL`。计时工具和那个默认不跑的计时测试里「两档都量」的地方保留，这样以后还能看到两档的差别。文档跟着改。

**2. 引擎这边：批量的命令不为没加载过的照片读整段历史。** 粘贴、同步、合并，以及一次给多张照片设参数、重置——目标照片里没加载过的，不重建它的栈：

- 一条查询成批取出这批照片各自需要的东西（库里的编号、游标、步数、当前那份设置），不要一张一张地查。
- 用当前那份设置算出新的设置，照旧产出「已经算好的操作」交给提交那一步。
- 已经加载在缓存里的照片，照旧走内存里的栈（它是库里那行的镜像，两边一致）。
- 规矩一条都不许破：步数、裁剪、重做段、照片行上的镜像，必须和「把栈整个读出来再提交」的结果**完全相同**。你要有一个测试证明这一点：两个一模一样的小会话，一个走这条路，一个逐张加载，粘贴之后两边库里的每一张表都相同。
- 「先算好、提交、再换入」的次序不变；一万张仍然是一条事务。

**3. 库那边：写入器少碰盘。**

- 语句准备好之后复用，不要每推一步都重新准备。
- 已经知道游标就在最后一步的时候，不要执行「删掉游标之后的步」。
- 同一份快照的内容在一次写入器里只查一次、只比一次字节：后面的推送如果带来的是一模一样的内容，直接用第一次查出来的结果。**碰撞的规矩不变**：键相同时必须逐字节比对过，不同就另存一行加后缀。
- 写路径的六条不变量，每一条原来有测试的照旧通过；新加的捷径也要有测试。

**4. 再量。** 改完之后，两块盘上各量至少三轮，发行版，机器安静（照 `Scripts/rust-budget.sh` 里现成的判断办法，忙时报「测不准」）。三段拆开的数和动手前并排写。

- **目标**：机械盘上的中位数 **不超过 600 毫秒**（留出四成余量）；内置盘上不比动手前慢超过一成；每一轮送达的事件数仍然等于一万。
- **达不到**：把拆开的数、你试过的每一条办法和它各自省了多少，如实写进报告。不许为了让数好看而少做任何一件事。

**5. 计时工具顺手改两处。** 跑完之后把会话关干净（现在它直接退出，会话目录里留着日志文件）。输出里带上三段的拆数。
