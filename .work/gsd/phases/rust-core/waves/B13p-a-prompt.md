## 现在的起点（塔台看的，每一条你自己核）

- 照片表、快照表、历史步表都建好了，但**库里没有任何写它们的代码**。照片这一侧连「登记一张照片」都没有——它本来属于导入那一波（B15）。所以你要做最小的一份：登记、查找、列出。
- 引擎里每张照片的历史栈是这样起步的：第一步存默认设置，标签是 `seed`，游标在 0。库里要和它一致：登记一张照片时，写下第 0 步（标签 `seed`，默认设置的快照），照片行的游标是 0，当前快照是默认设置的那一个，处理版本号的镜像也是默认设置里的那个。照片行的当前快照那一列不许为空，所以这一步不能省。
- 照片对外的标识是它的通用唯一标识（`uuid`，文本）；表里的整数 `id` 是库内部用的。会话标识的生成办法第一波已经有了（读操作系统的随机源），照片标识照它做，不许自己手写随机数。

## 要做的

**只动 `crates/lightamer-catalog` 这一个 crate**（可以新增它对 `lightamer-history` 的依赖；分层表允许第 3 层依赖第 2 层）。引擎、命令行、历史模型都不碰。

**1. 照片的最小登记。**

- 登记：给会话根和照片的绝对路径，再给文件名和文件大小（拍摄时间等检索列这一波先留空）。在同一个事务里写三样：照片行（路径按第一波的规矩换算后存进去）、默认设置的快照、第 0 步。返回照片的记录（整数 `id`、`uuid`、存进去的路径）。
- 查找：按 `uuid` 查，按整数 `id` 查。列出：会话里全部照片的 `uuid`，数量多的时候不能把全部行读进内存只为取标识。
- 同一个路径登记两次怎么办，你定一条规矩并写进文档（塔台的建议：拒绝，什么都不写）。

**2. 历史的写接口。** 一个写入器：打开一个事务，可以往里面推若干步，最后提交。推一步的内容是：哪张照片、这一步的标签、**已经算好的新设置的规范 JSON**。每推一步，在事务里做：

- 写快照：拿 JSON 算出键，去查。查不到就插入。查到了就**逐字节比对**：相同，复用这一行；不同，就是哈希碰撞，另存一行，键加上后缀（比如 `#2`，再碰撞往下数），并把碰撞这件事报告给调用者。
- 删掉游标之后的历史步（重做的那一段），再在游标加一的位置插入新的一步。
- 步数超过上限（200）：从最旧的开始裁，剩下的步重新从 0 编号，游标跟着移。
- 更新照片行：游标、当前快照的键、处理版本号的镜像，写在**同一条 `UPDATE`** 里。镜像的值取自这份设置里的处理版本号，不许依赖列的默认值。
- 推一步返回：这一步的键、有没有碰撞、新的游标和步数。

只推一步就提交，是它的一个简单用法（后一半的多数命令是这样用的）；一次推一万张照片各一步、只提交一次，是另一个用法（后一半的批量粘贴）。

**3. 移动游标。** 撤销、重做、跳到某一步，在库里只是游标变了：不新增任何步，一条 `UPDATE` 同时改游标、当前快照的键、处理版本号的镜像。目标位置越界是错误，什么都不写。返回移动之后当前设置的规范 JSON。

**4. 读出一张照片的历史。** 按编号从 0 到最后，每一步的标签和快照的规范 JSON，外加游标在哪。读出来之后，别人能用历史模型现有的接口把它重建出来。

**5. 孤儿快照。** 一条查询查出所有孤儿：没有任何历史步引用它，也不是任何照片的当前快照。关会话的时候清一次（在关会话的那个事务里）。校验报告里报告孤儿的数量和悬空的引用——第一波的校验如果已经查了这一项，核对它和你这里的定义一致；没查就补上。

**6. 崩溃。** 事务提交了一半被打断，库回到事务之前；提交完了的，一步不少。这些是 SQLite 保证的，你这一波要做的是**用测试证明它**：在一个子进程里开一个事务、推几步、提交，然后被强杀；父进程打开同一个库，看到的是提交过的那些步，一条不多一条不少。（测试里只许起你自己的测试程序，只许强杀你自己刚起的那个进程。）

## 测试

每一条行为一个测试，名字能看出测的是什么。**全部在临时目录里跑**，自己建、自己删；不碰用户照片库 `/Volumes/UNITEK/Cloud Drive/QSync/Medias/Photos/Workspace`（不读、不列目录），不写用户真实的应用支持目录。

- **六条写路径不变量**（T-B1 末尾），每条至少一个测试：
  1. 一步是一条事务：推一步之后，快照、历史步、照片行三处都变了；推到一半出错，三处都没变。
  2. 移动游标只改照片行；历史步一行没多没少。
  3. 超过 200 步：裁掉最旧的，剩下的编号从 0 连续，游标对得上；被裁的步原来引用的快照，如果没人再引用，关会话时被清掉。
  4. 照片行上的当前快照和处理版本号，永远和游标那一步的快照一致（推几步、来回移动游标之后各核一次）。
  5. 处理版本号不是 1 的设置，照片行上的镜像等于设置里的那个值。
  6. 哈希碰撞：**测试里要能注入一对碰撞的键**（给键的计算留一个只给测试用的注入口）。两份不同的设置得到同一个键时，库里是两行快照，各自的历史步指向各自的那一行，谁也没有被当成谁；调用者被告知发生了碰撞。
- 登记：写进去的照片行、第 0 步、默认快照都对；按 `uuid` 和按 `id` 都查得到；列出和登记的数量一致；重复登记按你定的规矩办。
- 读回：推几步、来回移动游标之后读出来，步数、标签、游标都对；**用历史模型现有的接口重建出来的栈，和写进去之前的栈一步步相同**（当前设置、每一步的标签、游标）。
- 一次推一万张各一步、只提交一次：一万张照片行都对；全程只有一条事务（用 SQLite 的更新计数或日志验证）。
- 孤儿：关会话之前有孤儿，关会话之后没有了；还有人引用的快照一行没少；校验报告里的数量和查询一致。
- 崩溃：见第 6 节。
