# GUI 计时 · Lumen RAW 2.3.0 (macOS arm64)

> 对象：LUMEN RAW 官方发行版 2.3.0（Python + PySide6 + PyInstaller，非原生）。测量日期 2026-11-25，机器 Apple M4 / 16 GB / macOS 27.3，HEAD `c8bd209bd2c3ab76f905c055d6747e6d94d82811`。

- **N=10000 未测**：产品硬限制 `a library holds at most 2000 photos`（`library.add` 直接报错），按上限补测 1999。如实记录，未缩小到「伪 10000」。
- **M3b**：粘贴只写编辑状态与条目文字标记，**缩略图不随粘贴重绘**（三档同一条 `edit.copy` 均未触发 THUMBNAILS 活动；强变化只核 199 张）。实证：把 +2.00 EV 套到 199 张后，首条缩略图区域帧差 **1.83/255**（仅文字标记抗锯齿），空转 3 s 的对照帧差 0.00。
- **M3c**：粘贴在 GUI 线程同步执行；2000 张时探针（`app.status` 每 200 ms）出现 ≥2.0 s 无响应，期间无法开图。

**判定句**：
- **打开等待合格**（懒渲染）：冷启动大头是 PyInstaller 解释器引导（≈3.1 s），真正解码 + 预览渲染只有 **1.18–1.29 s**；热切换 **0.98 s**。无 CIRAW 式长挂起，`#24` 的「换解码器能否救回用户等待」在此项上没有可救空间（解码只占 ~1 s）。
- **编辑等待 0.854 s 属架构原因**：每次提交都重跑整条开发管线（`engine.process`）再合成画布，且固定 180 ms 防抖；换解码器不改变这一段（输入平面已驻留内存）。
- **批量粘贴不构成等待瓶颈，但不合格于「可见反馈」**：1999 张 4.6 s、每张 2.3 ms，纯元数据；代价是 GUI 线程被占满（≥2 s 无响应）且缩略图不反映编辑——用户无法确认哪些照片被套用。该缺陷与解码器无关，属**架构/代码原因**（O(N²) 条目查找 + 无后台队列 + 无缩略图失效通知）。

## §2 打开 / 编辑等待数字

冷启动阶段拆分（n=5 中位）：`open` 返回 0.02 s；LaunchServices + 进程引导到窗口出现 3.06 / 3.06 / 3.06 s（三样张，眼底基本一致）；窗口出现到就绪 1.19 / 1.29 / 1.18 s。7RM5 与 Z8 的 rep0 各有一个 5.6 / 5.3 s 的离群（首个 rep 的冷页缓存），其余四rep 4.17–4.38 s。

> **就绪判据修订（自审后）**：第一版用 `cap.py` 的 `diff_base > 1 或 std > 8`，空 UI 的 std≈23 恒过门，导致 GFX/Z8 把「空窗稳定」当成就绪（4.09/4.10 s 是假值）。改为「只认与首帧（空 UI）的差异 > 1」后重测，得到上表；重测的就绪帧画布统计 mean 91.9–119.2 / std 66.2–78.2（真空视口为 mean 9.3 / std 21.5），可排除假阳性。

Lumen 的打开路径（源码 1.6.2 + 发行版行为一致）：`engine.load_image(path, preview_limit=1600)` → LibRaw `unpack()` + `postprocess(use_camera_wb, output_bps=16, gamma=(1,1))` → 缩到 1600 px。**一次解码、一次渲染**，没有「先内嵌预览后全解码」两级；因此窗口后 1.18–1.29 s 就是全部解码+首屏成本（100 MP RAF 4.35 s，比 85 MB ARW 的 4.25 s 只多 0.1 s）。

编辑路径：`changed()` → 180 ms 防抖 → 后台 job `engine.process(source, edits)` → `update_display` 合成 → 画布重绘。状态栏自报渲染段（截图证据 `frames/probe1.png`）：**84 ms**；用户可见的 854 ms 中，180 ms 是固定防抖、84 ms 是渲染段（状态栏自报），其余 ≈590 ms 是排队 + 画布合成/重绘 [INFERENCE：未逐段插桩]（口径差已注明：本项以画布稳定为准，不用状态栏数字）。

热切换（`photo.open`）：命令 85 ms 返回，画布 0.60 s 变（先变黑再出图），0.98 s 稳定。**热切换不比冷启动的「图后段」差**（0.98 vs 1.18–1.29 s），说明解码器是同一段成本；Alcedo 那种「热切换远差于冷启动」的形态在此不存在。

## §3 批量粘贴数字

见 §0 表。补充：

- 粘贴语义（源码 `commands.py::edit_copy`）：`extract_look` → 逐目标 `apply_look` + `validate` + `context.apply`（写 history）；**不触碰像素**，不触发解码/渲染。
- 目标必须在库内，否则 `context.add([other])` —— 本次全部预导入，故不计。
- 每张成本随 N 上升：0.63 → 1.16 → 2.30 ms/张，`film_item(path)` 为 O(N) 线性查找，总复杂度 O(N²)。
- 选择 1999 张本身耗时 **12.76 s**（GUI 线程），比粘贴长 2.8 倍——批量操作的真实痛点在这里，不在粘贴。

## §4 归因拆解

| 段 | 数字 | 依据 |
|---|---|---|
| 粘贴本身（1999 张） | 4.60 s = 2.30 ms/张 | 命令往返；期间无解码（目标像素从未被读） |
| 粘贴期间 GPU/CPU | **未采样** | 只有命令语义（`edit_copy` 不触碰像素）与「粘贴期间无 RENDER/THUMBNAILS 活动」的代码推断，未做 CPU/GPU 计数器 |
| 单张缩略图（导入期） | 未单独计时 | 代码路径：`library.thumbnail()` 走 `rawpy.extract_thumb()`（内嵌 JPEG）+ PIL 缩到 128×80；无 preview 的才退回 `load_image(path,144)` 全解码。**属「读文件 + JPEG 解码」量级，不含去马赛克** [INFERENCE：未单独计时] |
| 整条 headless 渲染（参照） | 4.28 s（`lumen-cli render --size 800`，含进程启动 ~1 s） | 实测，同机同文件 |
| 排队/阻塞 | 粘贴同步在 GUI 线程；2000 张时探针 ≥2.0 s 无响应 | 探针线程每 200 ms 调 `app.status` |
| 缩略图刷新 | **不存在**：粘贴不使缩略图失效 | 帧差 1.83/255（文字标记），空转对照 0.00 |

判定：**批量等待 = 架构/代码原因**（O(N²) 查找 + 前台同步 + 无缩略图失效）；**解码器原因占比 0**——粘贴期间没有任何解码发生。唯一与解码相关的是导入期缩略图，走内嵌预览，成本可忽略。

## §6 这个 App 做对了什么（懒在哪一层）

1. **一次解码、常驻内存**：打开时把 RAW 解到 1600 px 预览平面并只保留这一份，后续编辑在预览平面上做，不再碰原文件——热切换 0.98 s 与冷启动图后段 1.18–1.29 s 基本同量级（热切换略快），证明没有重复解码。
2. **缩略图走内嵌 JPEG**（`rawpy.extract_thumb`），不解马赛克；导入 100 张 80 ms 返回、1000 张 0.62 s，全部后台 4 张一批。
3. **编辑异步 + 防抖**：`JobScheduler` 单所有权、按活动优先级排队，渲染在后台线程，GUI 只在 `finish` 回调里合成——所以 854 ms 的等待里界面仍可操作。
4. **粘贴是纯元数据**：不逐张解码、不逐张渲染，100 张 63 ms。

**做错的**：缩略图与编辑状态没有失效联动（用户看不到套用结果）；批量选择/粘贴在 GUI 线程同步跑，2000 张量级直接冻结 2–5 s；条目查找 O(N²)。

## §8 风险与未验项

- **未采样**：粘贴期间 CPU/GPU 占用；缩略图单张成本（只有代码路径 + 导入总时长，§4 标了 INFERENCE）。
- **未测**：100% 放大细节读取（`DETAIL`）、导出、AI、空调度；`edit.get` 的 `target_exposure` 字段为 null（该命令返回 `changes`/`recipe`，实际核验走 `changes: ["曝光 0 → +2.00"]`）。
- **「GUI 线程」是源码推断**：粘贴同步性来自 v1.6.2 源码 `sync_look`/`control.Bridge.call` 与探针阻塞实测，未在 2.3.0 二进制内插桩。
- **onset 门限偏置**：`cap.py` 的 onset 判定要求 `len(frames) > 3`，hot/edit 的 onset 值可能含约 +0.15 s 的采样偏置；就绪值不受影响。

- 本地源码树是 v1.6.2+1，发行版是 2.3.0——代码引用只作**机制说明**，数字一律以发行版实测为准。
