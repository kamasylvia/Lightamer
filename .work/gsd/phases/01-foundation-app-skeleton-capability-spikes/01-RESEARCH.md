# Phase 1 Research: Foundation, App Skeleton & Capability Spikes

**Researched:** 2026-08-03
**Revised:** 2026-08-04 (multi-target + Tuist, Layer skeleton, state isolation, module API contracts)
**Status:** Ready for planning (plans must match the multi-target structure in D-02/D-03/D-03a/b/c)
**Scope:** Implementation detail for Phase 1 (FOUND-01/02/03/05/06/07, RAW-01/02/04/05/06). Project-level decisions (macOS 27 floor, CIRAW 9 boundary, Darktable pixelpipe architecture) were locked in prior research (STACK/ARCHITECTURE/PITFALLS) and are not re-litigated here.

## Summary

Phase 1 stands up a **multi-target macOS 27 app generated by Tuist** (D-02/D-03 revised) — the skeleton is five Swift modules whose boundaries are **compiler-enforced** via Swift access control (`public` = cross-module API surface, `internal` = implementation detail). The three subsystems in flight are: (1) **LightamerCore** framework — `RAWDecoder` wrapping `CIRAWFilter` with RAW 9 opt-in + RAW 8 fallback + ImageIO metadata, the `MetalContext` actor with two-layer dispatch + lazy PSO cache + function-constants, the `IOPModule` protocol + `v50_order` table ported from Darktable's `iop_order.c:298-415`, the **Layer abstraction skeleton** (`protocol Layer` + `struct LayerStack`, D-03a), and the shared value types (`AppError`, `ROI`, `WorkingSpace`, `DecodedImage`); (2) **LightamerIOP** framework — the `PassthroughModule` proving the pixelpipe chain end-to-end; (3) **Lightamer** app — the SwiftUI shell, `EditorMTKView` `NSViewRepresentable`, and the four isolated `@Observable` state objects (SessionState/EditorState/ExportState/InspectorState, D-03b). Two independent spikes (CIRAW 9 boundary, 100MP Metal perf) run on isolated spike branches.

The decoupling payoff is real and immediate: because LightamerCore is a separate compilation unit, changing a Core `internal` cannot break IOP or app code; promoting a Core type to `public` is a deliberate API-surface decision; and the Phase 2 pixelpipe can be written layer-aware from line one (D-03a, the L005 countermeasure) because the `Layer`/`LayerStack` types are already `public` in Core. **Confidence is High** on the architectural shape (faithful port of Darktable's OpenCL→Metal mapping + standard Tuist multi-target pattern) and **Med** on exact RAW 9 behavior on macOS 27 beta (camera list still expanding, `colorNoiseReductionAmount`/`detailAmount` are no-ops under RAW 9 per WWDC26/305).

One nuance worth flagging up front: **D-13 (no zoom/pan)** means the Phase 1 MTKView is a near-static blit — full zoom/pan (PERF-2) is a Phase 2/3 concern. And **D-15 (single `MTLCommandQueue`)** is correct for Phase 1 but the spec should leave a clear seam (`commandQueue` as `private(set)`) for the Phase 11 low-priority export queue.

## Implementation Approaches

### 1. Tuist Project.swift for Multi-Target macOS 27 App  [REWRITTEN — replaces XcodeGen]

**Confidence: High** — Tuist's `Project.swift` is a Swift-typed manifest; the multi-target + dependency-graph pattern is well-documented and widely used. `.metal` files compile to the default library via Xcode's standard build rule (Tuist defers compilation to `xcodebuild`).

> **Module placement note (applies to all subsequent sections):** the `Project.swift` IS the module boundary declaration. Each `Target` entry below becomes a distinct Swift module; the `dependencies:` array IS the directed acyclic dependency graph. Swift `import LightamerCore` / `import LightamerIOP` only resolve if the dependency edge exists in this manifest AND the imported symbol is `public`.

**Tuist API choice (verified against current Tuist 4.x docs and community examples):**

Tuist supports two `Target` construction spellings:
- **Initializer form** (works in all versions, broader community examples): `Target(name:platform:product:bundleId:deploymentTarget:...)`
- **Static method form** (modern Tuist 4.x preferred — `Target.target(name:destinations:product:deploymentTargets:...)`, where `destinations: [.macOS]` replaces `platform: .macOS` and `deploymentTargets: .macOS("27.0")` replaces `deploymentTarget: .macOS("27.0")`)

Both produce identical `.xcodeproj` output. **Recommendation: use the modern static-method form** (`Target.target` + `destinations` + `deploymentTargets`) — it is the current Tuist 4.x recommendation and supports multi-destination evolution. The skeleton below uses it. If the installed Tuist version rejects it, fall back to the initializer form (a mechanical translation: `destinations: [.macOS]` → `platform: .macOS`, `deploymentTargets: .macOS("27.0")` → `deploymentTarget: .macOS("27.0")`).

**Key manifest facts (verified against Tuist docs + community):**
- **`.target(name:destinations:product:...)`** is the modern static factory. `destinations: [.macOS]` is the multi-destination replacement for the legacy `platform: .macOS`. `deploymentTargets: .macOS("27.0")` sets the per-target floor. (Older `Target(name:platform:product:deploymentTarget:)` initializer still works and is mechanically equivalent.)
- **`product: .framework`** emits a framework target whose product is `LightamerCore.framework`. App target embeds it via the `dependencies: [.target(name: "LightamerCore")]` edge (Tuist auto-adds "Embed Frameworks" build phase + `@rpath` lookup).
- **`product: .app` / `.unitTests` / `.uiTests`** are the app, unit-test, and UI-test product types. UITests must depend on the **app** target (not Core) — they drive the running app.
- **`dependencies: [.target(name: ...)]`** is the dependency-graph edge. It is transitive at link time but **NOT at the `import` level**: the app can `import LightamerIOP` only because it has a direct `.target(name: "LightamerIOP")` edge; it does NOT implicitly gain `import LightamerIOP` transitively through Core (Core has no IOP edge anyway). This is the **module-boundary enforcement point** — remove the edge and `import` fails at compile time.
- **`.metal` files need NO custom build rule.** Tuist routes them to Xcode's "Compile Sources" phase automatically; Xcode's default Metal build rule emits `default.metallib` into the framework/app bundle. Read it at runtime via `device.makeDefaultLibrary(bundle:)`. Verified: function-constants (`[[function_constant(N)]]`) work unchanged because compilation is standard Xcode Metal toolchain under the hood.
- **`resources: ["LightamerCore/Resources/**"]`** picks up `.metal` files alongside any String Catalog `.xcstrings`, ICC profiles, or fixtures. **Do NOT double-list** `.metal` under both `sources` and `resources` — that is a build error. Convention: put iop `.swift`+`.metal` pairs together in `LightamerIOP/Sources/` and let Tuist classify them.
- **`infoPlist: .extendingDefault(with:)`** generates the Info.plist while injecting custom keys (document types). `.default` generates a minimal plist. Avoid hand-writing `Info.plist` files — Tuist's generation is the type-safe path.

**`tuist generate` workflow + `.gitignore` (Tuist convention):**

Tuist's convention is: **do NOT commit the generated `.xcodeproj`** — commit only `Project.swift`, `Tuist/Config.swift`, and sources. The project is regenerated on every checkout.

```gitignore
# .gitignore — Tuist conventions
*.xcodeproj
*.xcworkspace
DerivedData/
Derived/
.tuist/
Tuist/Dependencies/
Tuist/Cache/
# Keep: Project.swift, Tuist/Config.swift, Sources/, Resources/
```

- `tuist generate` reads `Project.swift` and emits `Lightamer.xcodeproj`.
- `tuist graph` renders the target dependency graph (useful for verifying the Core←IOP←app DAG).
- `tuist edit` opens the manifest in Xcode for type-assisted editing.
- **`Config.swift`** (in `Tuist/`) is optional for a single-project setup; it is required only when you add `tuist install`-managed dependencies (e.g., libwebp/libavif in Phase 11). Phase 1 has zero external deps, so `Config.swift` can be minimal or omitted.

**Function constants in `.metal` (D-17) — verified compatibility:**
Tuist does not need a special flag. Function constants are declared with `[[function_constant(N)]]` in `.metal` source and consumed via `MTLFunctionConstantValues` + `MTLComputePipelineDescriptor.functionConstants` at the Swift side. The `.metal` file compiles normally into the default library; specialization happens at PSO-creation time, not at file compile time. Confirmed by Apple's *Using function specialization to build pipeline variants* doc and MSL spec. **Confidence: High.**

**Gotchas:**
- **`makeDefaultLibrary(bundle:)` must target the RIGHT bundle.** `LightamerCore.framework` contains its own `default.metallib` (from `LightamerCore/Resources/`); the app's `Resources/` may have a separate one. At runtime, resolve via `Bundle(for: SomeCoreClass.self)` to find the Core framework's bundle, NOT `Bundle.main`. If Core has no class to anchor `Bundle(for:)`, expose a `public enum CoreBundle { static let module = Bundle(for: ...) }` or use the SPM-style `Bundle.module` pattern adapted to Tuist. **This is the #1 cross-module Metal gotcha** — verify in the Spike B app.
- **Deployment target consistency across the DAG.** All five targets must declare `deploymentTargets: .macOS("27.0")`. If Core is `.macOS("27.0")` but IOP is accidentally `.macOS("14.0")`, `xcodebuild` warns about the mismatch and may produce subtle SDK-resolution bugs. The project-level `options.deploymentTargets` is a fallback default — set it per-target too for safety.
- **Hardened Runtime + Metal** (DIST-5): `ENABLE_HARDENED_RUNTIME: YES` is fine for Metal compute (no JIT). Library Validation can stay on for v1 since there are no third-party dylibs. Revisit if libwebp/libavif (Phase 11) need different handling.
- **`INFOPLIST_KEY_*` shortcuts** available in raw `xcodebuild` are NOT directly available in Tuist's typed DSL — use `infoPlist: .extendingDefault(with: [...])` dictionary instead.
- **Embedded frameworks + signing.** For non-App-Store distribution (DIST-2 Developer ID), "Embed & Sign" is correct for `.framework` products. Tuist's `.target(name:)` dependency auto-selects this; verify the build phase says "Embed & Sign" not "Embed" in the generated project.

### 2. CIRAWFilter + RAW 9 Opt-in (macOS 27)  [module placement note added]

**Confidence: Med** — RAW 9 API surface is documented but beta behavior is still settling (camera list, no-op keys). Fallback to RAW 8 is **High** confidence.

**Module placement:** `RAWDecoder`, `DecodedImage`, `RAWTechnicalParams`, `CaptureMetadata` all live in **`LightamerCore/Sources/Decode/`** and MUST be `public` (the app target consumes them via `EditorState`). The `CIRAWFilter` instance itself is an implementation detail — it stays `internal` to the `RAWDecoder` class (never exposed cross-module). The `rawUTIs` set and the `decodeRaster` helper are `private`/`internal`.

**Instantiation pattern** (D-21, D-22, D-23, D-24):

`CIRAWFilter` is not a standalone Swift class — it's the modern spelling of `CIFilter.filterWithImageURL(_:options:)`. The Swift entry point is `CIFilter(imageURL:options:)`, which returns a `CIFilter` whose `outputImage` is the decoded `CIImage`. Properties are read/written via `CIRAWFilterOption` keys (`kCIInputDecoderVersionKey`, `kCIInputNeutralChromaticityXKey`, etc.). The header `CIRAWFilter.h` is the canonical reference.

```swift
// LightamerCore/Sources/Decode/RAWDecoder.swift
import CoreImage
import CoreImage.CIFilterBuiltins
import ImageIO

public enum AppError: Error, LocalizedError {          // also used by §6/§7 — public in Core
    case unsupportedFile, noRAWDecoder, decoderInitFailed
    case metalDeviceUnavailable, metalPSOFailed(String)
    case memoryExceeded
    case cancelled
    public var errorDescription: String? { /* … */ }
}

public struct DecodedImage: Sendable {                 // public value type — crosses module boundary
    public let ciImage: CIImage
    public let rawTech: RAWTechnicalParams
    public let capture: CaptureMetadata
    public let segmentationSkyMatte: CIImage?           // iPhone ProRAW only (L004)
    public let decoderVersionUsed: DecoderVersion
    public enum DecoderVersion: String, Sendable { case v8, v9 }
}

public final class RAWDecoder: @unchecked Sendable {   // actor or @unchecked — see §7

    /// Unified entry for RAW + non-RAW (D-24). Internally branches:
    /// - RAW UTIs (CR3/NEF/ARW/RAF/RW2/ORF/DNG/IIQ/3FR/PEF/RWL/X3F) -> CIRAWFilter
    /// - Raster UTIs (JPEG/HEIC/PNG/WebP/TIFF/PSD-flat) -> CGImageSource
    public func decode(_ url: URL) async throws -> DecodedImage {
        let uti = (CGImageSourceCreateWithURL(url as CFURL, nil)
                   .flatMap { CGImageSourceGetType($0) }) ?? "public.data" as CFString
        if Self.rawUTIs.contains(uti as String) {
            return try await decodeRAW(url)
        } else {
            return try decodeRaster(url, uti: uti as String)
        }
    }

    internal func decodeRAW(_ url: URL) async throws -> DecodedImage { /* … */ }
    internal func decodeRaster(_ url: URL, uti: String) throws -> DecodedImage { /* … */ }

    internal static let rawUTIs: Set<String> = [        // internal — not part of public API
        "public.canon-cr2", "public.canon-cr3", "com.nikon.raw-image",
        "com.sony.raw-image", "com.fuji.raw-image", "com.panasonic.raw-image",
        "com.panasonic.rw2-image", "com.olympus.raw-image", "com.pentax.raw-image",
        "com.leica.raw-image", "com.hasselblad.3fr", "com.phaseone.iiq",
        "public.adobe-dng", "com.sigma.x3f"
    ]
}
```

(Full `decodeRAW` body — probe `supportedDecoderVersions`, set `decoderVersion`, build filter, read three metadata classes — is unchanged from the prior research; see the `CIRAWFilter.h` reference in Sources.)

**Key API facts (verified from `CIRAWFilter.h`):**
- `CIFilter(imageURL:options:)` is `NS_AVAILABLE(10_5, 10_0)` — always available. Returns `CIFilter?`.
- `kCIInputDecoderVersionKey` accepts `NSString`/`NSNumber`. The Swift spelling in modern SDKs is `CIFilter.RawDecoders.version8` / `.version9` (an enum imported from the `RawDecoders` typedef).
- `kCISupportedDecoderVersionsKey` is **read-only**; setting raises an exception. Probe it on a scratch filter, then set `decoderVersion` on the real one.
- `kCIInputNeutralChromaticityXKey`/`YKey`: `NSNumber (float)`. **No direct Kelvin slider** — convert K/tint → xy in Swift (research STACK.md boundary table).
- `kCIInputBaselineExposureKey`, `blackLevel`, `whiteLevel`: all `NSNumber (float)`.
- `kCIInputSemanticSegmentationSkyMatteKey` (macOS 11+): returns a `CIImage` **only for iPhone ProRAW embedded mattes** — silently nil for DSLR/Mirrorless RAW. (L004)
- **RAW 9 no-op keys** (WWDC26/305 verbatim): `colorNoiseReductionAmount`, `detailAmount`, `moireReductionAmount`. Effective keys under RAW 9: `exposure`, `luminanceNoiseReductionAmount`, `sharpnessAmount`, `contrastAmount`. The decoder-version-gated behavior means the RAWDecoder must NOT promise these sliders do anything under RAW 9 — the UI must hide/disable them when `decoderVersionUsed == .v9`.
- `supportedCameraModels` (`+ (NSArray<NSString*> *)supportedRawCameraModels`, macOS 10.15+): use for a "is this camera known" pre-flight, not for gating decode (Apple decodes by UTI, not model).
- **New in macOS 27** (WWDC26/305): RAW 9 supports "hundreds of models" at GA — broader than the early-beta X-T5/X-T50 subset. The spike (§8) confirms per-camera support.

**Gotchas:**
- **`CIFilter(imageURL:options:)` returns the SAME instance semantics as `CIRAWFilter`** — but Swift's static typing makes it a `CIFilter`, so all RAW-specific keys must be read via `setValue(_:forKey:)` / `value(forKey:)` (string-keyed KVC). The `CIFilter.CIRAWFilter` Swift overlay (recent SDKs) provides typed properties — check what's exposed in the macOS 27 SDK at build time and prefer the typed surface where it exists.
- **Two `CIFilter` instantiations per decode** (probe + real) doubles init cost. The probe's `supportedDecoderVersions` is a per-file property (the SAME image always reports the same list), so cache it in a `RAWDecoder` LRU keyed on file URL + mtime.
- **Draft Mode** (`kCIInputAllowDraftModeKey`) speeds decode at the cost of quality — useful for thumbnail generation (Phase 9), NOT for the editor viewport.
- **`kCIInputEnableVendorLensCorrectionKey`** defaults to `true` if the RAW contains lens opcodes (DNG OpcodeList). Leave it on for v1 — manual lens correction (IOP-GEO-03) is Phase 4.
- **Adobe DNG (RAW-02)** "just works" — Apple's DNG support is the universal fallback (STACK.md RAW Format Support). No special path needed; the UTI is `public.adobe-dng`.

**⚠ DECISION REVIEW: D-22 (RAW 9 default + auto-fallback).** The pattern is feasible. One nuance: when RAW 9 silently produces different output for a camera (e.g. applies its own ML denoise the user did not ask for), the user has no in-app signal that "RAW 9 happened." Sidecars should stamp the decoder version used (per PITFALLS CIRAW-2: "version-stamp sidecars with the decoder used"). **Recommendation:** `DecodedImage.decoderVersionUsed` is already `public` and carries this — reserve the sidecar field now even though sidecars are Phase 2.

#### 2.a Spike A back-port (append-only, 2026-09-16 — macOS 27.0 GM 26A428 measured, full report `spike-a-ciraw9-boundary.md`)

1. **RAW 9 coverage at GM = 69 models, NOT "hundreds"** (the §2 bullet above is wrong at GM). `CIRAWFilter.supportedCameraModels(with: .version9)` — GFX100S, X100VI, X-H2S, Z8, OM-1 II, X2D, R10 all **absent**; only X-T5/X-T50 among Fuji. D-22's fallback fires for most bodies; Plan 02's probe+fallback stands unchanged. Full lists: `.planning/spikes/spike-a-ciraw9-boundary/models.txt`.
2. **`supportedCameraModels(with:)` (macOS 27+)** — zero-cost camera-support probe without instantiating a filter; use it in `RAWDecoder` for the unsupported-camera fast path (cheaper than the two-instantiation probe; init costs 0.2–2.3 s cold, CR3 worst).
3. `supportedDecoderVersions` rawValues are strings: `"7"`, `"8"`, `"9"`, `"6.dng"`, `"7.dng"`, `"8.dng"`, `"9.dng"` — compare via `CIRAWDecoderVersion` constants' `rawValue`, never integers.
4. **No-op keys under v9 confirmed at GM with two mechanisms**: `colorNoiseReduction/detailAmount/moireReduction` flags drop to UNSUPPORTED on every v9 file; `luminanceNoiseReductionAmount` keeps its flag but is behaviorally inert under v9 (pixel-diff 0.00). `sharpnessAmount` is behaviorally inert at 1:1 under BOTH versions (scale-dependent). UI must gate on `decoderVersionUsed` (as §2 already prescribes).
5. **Phase One IQ4 150MP IIQ is NOT decodable by CIRAWFilter** (`[None]`, 0×0, preview only) — the unsupported-RAW typed-error path is real; the IQ4 sample is a Plan 06 fixture candidate; libraw fallback (D-24, v2+) has its first concrete case.
6. Lens-correction flag is per-file AND per-version (A7R V: UNSUPPORTED v8 → supported v9). No user-tunable CA/distortion/vignette at GM — the Phase 4 lens iop remains in scope.
7. ProRAW mattes: iPhone 12 Pro DNG surfaces `semanticSegmentationSkyMatte` at GM; other mattes nil per capture. Read opportunistically (D-23c).
8. Setting `decoderVersion = .version9` on a file that does not support it does NOT throw — CIRAW silently clamps to a supported version. `decoderVersionUsed` (not the requested version) must always be recorded.
9. `previewImage` present on every sample (GFX100S 4000×3000, Z8 full-size) — Phase 9 browser thumbnails should consume it, never first-decode.

### 3. MetalContext Dispatch Framework  [module placement note added]

**Confidence: High** for the dispatch shape (1:1 port of Darktable's `dt_opencl_enqueue_kernel_2d` pattern). **Med** for PSO cache sizing under the full 91-module set (Phase 1 only has ~1 kernel, so memory is trivial here; the real test is Phase 3+).

**Module placement:** `MetalContext`, `MetalError`, `PSOKey`, `CIContextPool` all live in **`LightamerCore/Sources/Metal/`**. The `MetalContext` actor and `MetalError` enum MUST be `public` (iops in LightamerIOP call `metal.dispatch2D(...)`; the app's EditorMTKView reads `metal.device`). The `PSOKey` struct and the `psoCache` dictionary are `internal` to Core (implementation detail). The `CIContextPool` is `internal` to Core — only Core's `RAWDecoder`/pixelpipe use it; the app never touches it directly.

**Two-layer dispatch API (D-19):**

```swift
// LightamerCore/Sources/Metal/MetalContext.swift
import Metal

public enum MetalError: Error, LocalizedError {
    case deviceUnavailable, functionNotFound(String), psoCreationFailed(String, Error?)
    case bufferAllocationFailed(Int)
    public var errorDescription: String? { /* … */ }
}

public actor MetalContext {                            // D-33 actor-isolated
    public let device: MTLDevice
    public let commandQueue: MTLCommandQueue            // D-15 single queue, private(set) seam for Phase 11
    private let library: MTLLibrary                     // internal — resolved from Core's own bundle
    private var psoCache: [PSOKey: MTLComputePipelineState] = [:]  // D-16 internal cache

    public init() throws {
        guard let device = MTLCreateSystemDefaultDevice() else { throw MetalError.deviceUnavailable }
        self.device = device
        guard let queue = device.makeCommandQueue() else { throw MetalError.deviceUnavailable }
        self.commandQueue = queue
        // CRITICAL: resolve metallib from the Core framework bundle, not Bundle.main.
        // See §1 gotcha: use Bundle(for:) anchored on a Core type.
        let coreBundle = Bundle(for: MetalContextMarker.self)
        self.library = try device.makeDefaultLibrary(bundle: coreBundle)
    }

    // ───────── High-level dispatch (D-19) ─────────
    public func dispatch2D(
        functionName: String,
        input: MTLBuffer, output: MTLBuffer,
        width: Int, height: Int,
        threadgroupSize: MTLSize = MTLSizeMake(16, 16, 1),
        constants: MTLFunctionConstantValues? = nil,    // D-17 function-constants
        configure: (MTLComputeCommandEncoder) -> Void
    ) async throws { /* … unchanged from prior research … */ }

    // Overload for texture-based dispatch (CIRAW CIImage → MTLTexture path)

**Key API facts:**
- `MTLCreateSystemDefaultDevice()` returns the Apple Silicon unified-memory GPU (D-14). `MTLDevice` is a class, not an actor — wrap the *queue* in your own actor (D-15).
- `device.makeDefaultLibrary(bundle:)` — the `bundle:` parameter is **mandatory** for framework targets. `Bundle.main` (the app) will NOT find Core's metallib. Anchor on a Core class via `Bundle(for: MetalContextMarker.self)`.
- `library.makeFunction(name:constantValues:)` is the function-specialization entry (async since macOS 11; throws if constants mismatch). The non-async `makeFunction(name:)` returns `MTLFunction?`.
- `device.makeComputePipelineState(descriptor:options:reflection:completionHandler:)` is the async PSO builder — do NOT use the synchronous `makeComputePipelineState(function:)` on the MainActor; it stalls.
- `encoder.dispatchThreads(_:threadsPerThreadgroup:)` (macOS 10.14+, Metal 2) is the non-uniform-grid dispatch — preferred over the older `dispatchThreadgroups`. Caps at `pso.maxTotalThreadsPerThreadgroup` per threadgroup (METAL-7).
- **Storage mode (METAL-4):** on Apple Silicon UMA, `.shared` everywhere is correct and simplest. Use `.private` for large GPU-only intermediates and stage through a blit encoder.

**Gotchas:**
- **`makeFunction(name:constantValues:)` requires `MTLFunctionConstantValues` to set ALL constants the function declares** — partial specialization throws at PSO creation. Mirror the `[[function_constant(N)]]` indices in a Swift table to avoid drift.
- **CIContext workingFormat `kCIFormatRGBAh` vs float32 output**: CIContext internally works in half-float for performance but you can render to a `.rgba32Float` texture — the cast happens at the render step. For the pixelpipe core (Phase 2+), prefer rendering CIRAW output to a float32 buffer ONCE, then running everything else as Metal buffer-to-buffer (per ARCHITECTURE.md §5).
- **`cacheIntermediates: false`** (CIRAW-4) is mandatory — without it, lazy CIImage chains on 100MP hold gigabytes of ROI descriptors. Verify with the Spike B 100MP test.
- **Single `MTLCommandQueue` (D-15)** is fine for Phase 1 (display-only, no contention). The seam to add a low-priority export queue (Phase 11) is just `device.makeCommandQueue()` again — keep `commandQueue` as `private(set)` and add a second property later.

#### 3.a Spike B back-port (append-only, 2026-09-16 — macOS 27.0 GM 26A428 measured, full report `spike-b-100mp-perf.md`)

1. **`CIContext.render(_:to:)` into an `.rgba32Float` MTLTexture writes EMPTY content on its FIRST use per process** — reproduced 6/6 processes on GM (this refines Plan 03's "render-to-MTLTexture silently writes empty" Phase 2 retest item: it is a first-use ordering issue, subsequent renders in the same process work). Phase 2: either warm up the render-to-texture path once at `CIContextPool` creation, or keep the validated **bitmap + `texture.replace(region:)`** path (1024×768 crop = 4–6 ms total). Plan 03's workaround is confirmed correct.
2. **`cacheIntermediates: false` validated (CIRAW-4 closed at GM)**: 100MP decode footprint peaks +0.3–0.6 GB per decode. BUT footprint ACCUMULATES across repeated decodes in one process (4.3–4.8 GB after ~11 full 100MP renders) — **`CIContextPool` must expose/trigger `clearCaches()` on image switch** (new Phase 2 requirement; without it a session drifts past the D-32 4 GB budget). Under accumulated pressure CoreImage can SIGSEGV in `CI::recursive_tile` instead of erroring.
3. 100MP float32 RGBA single plane (1.55 GB) allocates and renders fine on a 16 GB M4 (peak 2.0–2.8 GB ≈ plane × ~1.3 CI overhead) — the D-20 Phase 1 assumption is measured-safe.
4. A lazy CIRAW `CIImage` is NOT a frame cache: per-frame re-render at 2560×1440 = 330 ms (45–60MP) to 1020 ms (100MP X-Trans). Cached-plane path: 6.7–15.6 ms/frame → 60fps needs the Phase 2 per-module cache; <1 ms headroom at 100MP.
5. Decode cost is compression-variant dependent, not MP-dependent: GFX100S lossless-compressed RAF = 20.9 s vs uncompressed = 848 ms at identical 101.8MP (Apple's lossless-RAF decompressor at GFX scale is pathological at GM); Bayer 100MP (X2D 3FR) = 833 ms. RAW 9 does not speed up full-size decode (A7R V v9≈v8 766 ms; X-T5 v9 4.3× slower than v8). Progress UX for >2 s decodes is a Phase 9 requirement.

#### 5b. Layer Skeleton (D-03a — NEW)

**Design rationale (L005 + REQUIREMENTS LAYER-01..07):** Lightamer uses **Capture One-style adjustment layers** (each layer = independent iop params + mask + blend mode), NOT Darktable's global-pipe + per-iop-mask model. If the Phase 2 pixelpipe is built without layer-awareness, Phase 6 (Layers) becomes a rewrite. D-03a puts the **type skeleton** in Phase 1 so Phase 2 is layer-aware from line one; Phase 6 fills the implementation (traversal, compositing, mask rasterization).

**Recommended data structure (C1 model — per-layer iop chain):**

Research compared the two candidate models:
- **Darktable model:** global iop chain + per-iop mask. Each iop carries its own drawn/parametric/raster mask. Layers are a UI overlay, not a pipe-level concept.
- **Capture One model:** layer stack where each adjustment layer carries its **own** iop chain + its own mask + blend mode. The base layer carries the global iop chain.

Lightamer's REQUIREMENTS (LAYER-02 "每层独立 iop 参数", LAYER-06 "全局 iop 与图层共存") mandate the **C1 model**. The `LayerStack` therefore holds:
1. A **base layer** (background) carrying the **global iop chain** (the Darktable-style v50_order chain — this is where Phase 3+ creative iops live by default).
2. Zero or more **adjustment layers**, each carrying its **own per-layer iop chain** + a mask + a blend mode + opacity.

This makes Phase 6 feasible without Phase 2 rewrite: the Phase 2 pixelpipe processes the **base layer's** chain (a flat v50_order chain — identical to Darktable's model); Phase 6 adds per-layer chains that compose ON TOP via blend modes gated by masks. The pixelpipe traversal becomes: `for layer in stack: render layer.chain → composite onto accumulator with layer.blendMode * layer.mask * layer.opacity`. Phase 1 only defines the types; Phase 2 implements base-layer-only traversal; Phase 6 adds the multi-layer composite.

    public init() {}
    public func reloadDefaults(image: DecodedImage) async -> Params { Params() }
    public func commitParams(_ params: Params, into piece: inout IOPPiece) async {
        piece.paramsHash = Params().hashValue
    }
    public func modifyROIOut(_ roi: inout ROI, input: ROI, piece: IOPPiece) { roi = input }
    public func modifyROIIn(output roi: ROI, input: inout ROI, piece: IOPPiece) { input = roi }
    public func process(input: MTLBuffer, output: MTLBuffer,
                        roiIn: ROI, roiOut: ROI, piece: IOPPiece,
                        metal: MetalContext) async throws {
        try await metal.dispatch2D(
            functionName: "pass_through",
            input: input, output: output,
            width: roiOut.width, height: roiOut.height)
        { _ in }   // no extra bindings
    }
}
```

**Gotchas (IOPModule):**
- **`Params: Codable & Hashable` (FOUND-03) is mandatory** — Hashable feeds the cache hash, Codable feeds the sidecar (Phase 2). Structs with all-Codable fields auto-synthesize both. Don't use classes for params.
- **`opName` must match Darktable's `op` string** for any module that will later read/write Darktable-compatible sidecar entries (Phase 2). For internal-only modules (like the Phase 1 passthrough spike), a custom name is fine but document it.
- **The protocol has an `associatedtype`** which prevents `any IOPModule` from being used as a concrete type — use type-erased wrappers (`AnyIOPModule`) or generics at the pixelpipe level. The Phase 2 `ModuleRegistry` maps `opName → IOPModule.Type`.
- **`defaultColorspace` (REQUIRED in Darktable — `REQUIRED(dt_iop_colorspace_type_t, default_colorspace, ...)` at iop_api.h:97)** is mandatory. Phase 1's pass-through uses `.RGB`; the terminal trio (`colorin`/`colorout`/`gamma`) is Phase 2 work.

### 7. Swift Concurrency + State Isolation  [UPDATED with D-03b]

**Confidence: High** — this is the canonical Swift 6 + `@Observable` pattern, extended with the D-03b state-isolation contract (four separate `@Observable` objects, no god-object).

**Module placement:** All four state objects (`SessionState`, `EditorState`, `ExportState`, `InspectorState`) live in the **app target** at `App/Sources/` (under respective subdirs: `Session/`, `UI/` or a shared `State/`, `Export/`, `UI/`). #### 7a. State isolation contract (D-03b)

The four state objects and their ownership boundaries:

| State object | Owns | Does NOT own | Phase 1 scope |
|---|---|---|---|
| **`SessionState`** | current Session (folder URL), recent-sessions list, folder-watch status (Phase 9 FSEvents) | image data, layers, inspector panel | empty (no sessions); stub recent-list |
| **`EditorState`** | current image (`DecodedImage?`), layer stack (`LayerStack`), decode/error state, history stub | export queue, inspector panel selection | loads a file, holds the decoded image + empty layer stack |
| **`ExportState`** | export queue, recipes, progress | image data, inspector | empty (export is Phase 11) |
| **`InspectorState`** | currently-selected iop panel, panel expand/collapse state, metadata display fields | image data, layers | stub ("No Image Selected" placeholder) |

**Rule (D-03b):** views inject ONLY the state object they need. `SidebarView` takes `SessionState`. `EditorAreaView` + `EditorMTKView` take `EditorState`. `InspectorView` takes `InspectorState`. No view holds all four.

#### 7b. EditorState pattern (D-33, D-34, D-35)

```swift
// App/Sources/State/EditorState.swift — internal to app target
import SwiftUI
import Observation
import LightamerCore                 // for RAWDecoder, DecodedImage, LayerStack, AppError
import os

@Observable                                          // D-35 — replaces ObservableObject (macOS 14+)
@MainActor                                           // D-33 — UI isolation
final class EditorState {
    private(set) var image: DecodedImage?
    private(set) var layerStack: LayerStack?         // D-03a — skeleton; base layer only in Phase 1
    private(set) var decodeError: AppError?
    private(set) var isDecoding: Bool = false
    private var decodeTask: Task<Void, Never>?

    func load(url: URL, decoder: RAWDecoder, logger: Logger) {
        decodeTask?.cancel()                         // D-34 cancel previous
        decodeTask = Task { [weak self] in
            await MainActor.run { self?.isDecoding = true; self?.decodeError = nil }
            let signpost = OSSignposter(subsystem: "com.kamasylvia.lightamer",
                                        category: "decode")          // D-31
            let id = signpost.beginInterval("decode", "url:\(url.lastPathComponent)")
            do {
                let decoded = try await decoder.decode(url)   // runs off MainActor
                if Task.isCancelled { return }                 // D-34 cancellation
                await MainActor.run {
                    self?.image = decoded
                    self?.layerStack = LayerStack(baseLayer: BackgroundLayer())  // D-03a skeleton
                }
            } catch is CancellationError {
                logger.info("decode cancelled: \(url.path)")
            } catch {
                logger.error("decode failed: \(error.localizedDescription)")
                await MainActor.run { self?.decodeError = AppError(error) }  // D-25
            }
            signpost.endInterval("decode", id)
            await MainActor.run { self?.isDecoding = false }
        }
    }
}
// RAWDecoder.decode is async; not @MainActor — runs on background executor.
// Swift 6 enforces data-race safety: any mutable state in RAWDecoder must be actor-isolated.
```

#### 7c. Cross-state communication (without coupling)

The four state objects must not hold references to each other (that would re-create the god-object). Cross-state coordination flows through **SwiftUI View layer** or a **lightweight coordinator**:

| Coordination need | Mechanism (no direct state-to-state ref) |
|---|---|
| SessionState selects a file → EditorState loads it | The shared `ContentView` observes both; on SessionState selection change, it calls `editorState.load(url:)`. The states don't know about each other. |
| EditorState decode completes → InspectorState shows metadata | `ContentView` body reacts to `editorState.image` change and passes `editorState.image?.capture` into `InspectorView(capture:)`. No InspectorState→EditorState reference. |
| EditorState image changes → ExportState enables export | `ContentView` passes `editorState.image != nil` as a `Bool` binding into the export toolbar item. ExportState doesn't observe EditorState. |

**When a true coordinator is needed (Phase 2+):** if pixelpipe invalidation must cascade across state boundaries (e.g., changing a layer invalidates the editor render AND the export queue), introduce a small `@Observable Coordinator` (or a Swift `actor CommandBus`) that both states subscribe to — NOT a reference from one state to another. Phase 1 has no such need (display-only).

**Key facts:**
- **`@Observable` macro (Swift 5.9+, macOS 14+)** replaces `ObservableObject` + `@Published`. SwiftUI views observe via plain property access; only accessed properties trigger re-renders (more efficient than ObservableObject).
- **`@MainActor` on the class** makes all stored property mutation happen on the main thread — matches D-33.
- **`Task { … }` for background decode** inherits the actor context if not detached. To run truly off-MainActor, mark `RAWDecoder.decode` as `nonisolated`/`actor`-isolated.
- **Cancellation (D-34):** `Task.cancel()` propagates `CancellationError` at the next `try/await` boundary. Long-running CIRAW decode does NOT naturally respond to cancellation — wrap in `withTaskCancellationHandler` if you need to abort a stuck decode.
- **`OSSignposter` (D-31)** is the modern `os.signpost` Swift API. Instruments reads these intervals.
- **`Logger` (D-27):** `import os; let logger = Logger(subsystem: "com.kamasylvia.lightamer", category: "decode")`.

**Gotchas:**
- **`RAWDecoder` must be `Sendable`** for Swift 6 strict concurrency. Mark it `final class @unchecked Sendable` (if internally synchronized) or `actor`. The CIRAWFilter instance is NOT Sendable (it's a `CIFilter` subclass) — wrap each decode in a fresh `CIFilter` and return a value type (`DecodedImage`), or actor-isolate the `RAWDecoder`.
- **`@Observable` doesn't work with `@StateObject`/`@ObservedObject`** — use `@State` for the owner in SwiftUI views. Lifetime: `@State` survives view re-renders.
- **State-object lifetime:** own each state via `@State` in the `App` or `ContentView` (the root), and inject downward via initializer parameters or `.environment()`. Do NOT use a singleton — singletons make testing harder and violate Swift Concurrency's anti-global-state stance.
- **`MainActor.run { … }` vs `await foo()` on a MainActor-isolated function:** the latter is preferred (compiler inserts the hop). Use `MainActor.run` only when crossing from a non-isolated context.

### 9. Module API Contracts + Access-Level Strategy  [NEW — D-03c]

**Confidence: High** — Swift access control is the stable, compiler-enforced mechanism. The per-module `API.md` is a human-readable index (D-03c), enforced by code review; the compiler does the real enforcement.

#### 9a. The access-level strategy

Swift has four access levels. Lightamer uses three of them deliberately:

| Level | Meaning in Lightamer | Who can see it | Example |
|---|---|---|---|
| **`public`** | Cross-module API surface. Stable contract. Changing this is a breaking API change that surfaces compile errors at every call site in dependent modules. | Any module that imports the owning module. | `RAWDecoder`, `DecodedImage`, `MetalContext`, `protocol IOPModule`, `protocol Layer`, `struct LayerStack`, `enum V50Order`, `enum AppError`, `struct ROI` |
| **`internal`** (default) | Implementation detail of the owning module. Free to refactor without breaking other modules. | Same module only. | `PSOKey`, `CIContextPool`, `RAWDecoder.decodeRAW`, `rawUTIs`, `MetalContextMarker` |
| **`private`/`fileprivate`** | Implementation detail of a single type or file. | Same file/type only. | `psoCache` dict internals, helper functions scoped to one file |

**The decoupling payoff (why this matters):**
- Changing a Core `internal` (e.g., renaming `PSOKey` to `PipelineKey`) breaks **nothing** outside Core — no IOP or app compile error.
- Changing a Core `public` (e.g., removing a `RAWDecoder` method, or changing its signature) surfaces **compile errors at every call site** in IOP and the app. The breakage is loud, immediate, and localizable. This is the "compiler-enforced boundary" the user asked for ("未来可能的改动会很多，因此希望项目尽量解耦").
- Without module separation (single-target), ALL types are effectively `internal` to the one target — there is no `public` boundary, and "subsystem boundaries" are a convention enforced by code review alone. That convention erodes under deadline pressure. D-02's multi-target choice makes the boundary structural.

#### 9b. Public API surface per module (the contract)

This is the load-bearing table — every type listed here MUST be `public`; everything else in the module is `internal` or below.

**LightamerCore (framework) — public surface:**

Each module directory gets an `API.md` listing the public surface vs internal. This is a human-readable index, not a substitute for the compiler. Example for `LightamerCore/API.md`:

#### 9d. Compilation-enforcement examples

| Refactor | Effect |
|---|---|
| Rename `LightamerCore`'s internal `PSOKey` → `PipelineKey` | Compiles fine in IOP and app (they never saw `PSOKey`). Zero blast radius. |
| Change `RAWDecoder.decode(_:)` signature (a `public` method) | Compile error in `EditorState.load` (app target) AND in `LightamerTests`. Forces the caller to update. Loud, immediate. |
| Add a new `public` method to `MetalContext` | Compiles fine everywhere. The new method is opt-in. |
| Remove `protocol Layer` from Core (a `public` type) | Compile error in IOP (if any iop conforms) and app (`EditorState.layerStack` references it). Catastrophic — exactly the signal you want before accidentally deleting a contract type. |

## Validation Architecture

For Nyquist validation: what observable behaviors/edge cases must Phase 1 plans verify? **The test targets now span modules** — `LightamerTests` depends on Core + IOP and tests their `public` surfaces; `LightamerUITests` depends on the app and tests the running app via XCUI.

**Cross-module test access (important):**
- `LightamerTests` can test `public` types in Core and IOP directly (`import LightamerCore; import LightamerIOP`). It CANNOT see their `internal` types — those are invisible to the test target. If a test needs internal access, either (a) make the type `public` (preferred — it's genuinely part of the API), or (b) use a `@testable import LightamerCore` (works only if the test target can see the module's source, which Tuist configures via the `.target` dependency — `@testable` imports the module with internal access elevated).
- **Recommendation:** prefer testing through the `public` surface. Use `@testable` sparingly — it couples tests to implementation details, eroding the boundary benefit. Phase 1's tests should verify *structure* (RAWDecoder returns non-nil, MetalContext initializes, IOPModule conforms, LayerStack builds with a base layer) — algorithmic correctness tests are Phase 2 golden-image harness (D-28).

**Functional correctness:**
- RAW decode succeeds for at least one CR3, one NEF, one ARW, one RAF, one DNG, one HEIC, one JPEG, one PNG, one TIFF (RAW-01/02/04).

## Risks & Gotchas

Beyond what PITFALLS.md covers project-wide, Phase 1-specific risks:

1. **Tuist tool dependency (D-02a cost).** Tuist is a `brew install tuist` (or `mise install tuist`) dependency. If the build environment lacks it, `tuist generate` fails before compilation. **Mitigation:** pin the Tuist version in `Tuist/Config.swift` (`ProjectDescription` version must match the installed CLI). Document the install step in the README. CI (Phase 13) must install Tuist.

2. **Module-boundary migration cost (D-02 one-way).** Once `public` types in LightamerCore are consumed by IOP/app, changing them is a breaking change across modules. The `API.md` (D-03c) makes this visible, but the cost is real. **Mitigation:** the Phase 1 public surface should be MINIMAL — only what IOP/app/tests genuinely need. Promote types to `public` lazily; start with fewer and add as the dependency emerges. It is easy to add `public`; hard to remove.

3. **`Bundle(for:)` metallib resolution in a framework (§1 gotcha).** Core's `default.metallib` lives in `LightamerCore.framework`, not the app bundle. `device.makeDefaultLibrary()` (no bundle arg) reads from `Bundle.main` — WRONG for Core. Use `device.makeDefaultLibrary(bundle: Bundle(for: MetalContextMarker.self))`. **This is the single most likely "why is my Metal kernel not found" bug** — verify in Spike B before building the real MetalContext.

4. **`CIFilter.RawDecoders.version9` enum may not yet exist in the macOS 27 SDK at the time of writing.** The string spelling `"9"` passed via `kCIInputDecoderVersionKey` is a safer fallback if the typed enum isn't exposed. **Mitigation:** probe both at build time; prefer the typed enum when available.

5. **`CIContext.render(_:to: MTLTexture)` synchronous overload may block the MainActor if accidentally called there.** The async `render(_:to:commandBuffer:bounds:colorSpace:)` is preferred but requires a `MTLCommandBuffer`. **Mitigation:** `RAWDecoder.decode` is `async` and runs off-MainActor; `CIContextPool` is actor-isolated.

6. **`.rgba32Float` texture creation on 100MP is ~1.6GB.** `MTLDevice.makeTexture` can return nil if `recommendedMaxWorkingSetSize` is exceeded. **Mitigation:** check before allocation; if exceeded, the Phase 2 tiling path engages (D-20).

7. **CIRAWFilter caching across decode calls is undocumented.** Re-instantiating `CIFilter(imageURL:options:)` for the same URL may re-decode from scratch. **Mitigation:** the MipmapCache (Phase 9) caches the *decoded* buffer; Phase 1 just measures the cold cost.

8. **`MTKView.preferredFramesPerSecond = 60` may exceed the display's refresh rate on ProMotion (120Hz) or fall below on 30Hz external displays.** **Mitigation:** for Phase 1 (static blit), set `isPaused = true` and `enableSetNeedsDisplay = true` — redraw only on source change.

9. **`os.Logger` string interpolation uses OSLogMessage runtime interpolation** — interpolating user-controlled strings can leak data into system logs. **Mitigation:** mark user-data interpolations as `.private` (e.g. `logger.info("opened \(url.path, privacy: .public)")` — file paths are fine to log public).

10. **`@Observable` macro requires `import Observation` and a minimum macOS 14 deployment** — satisfied by the macOS 27 floor but worth flagging in case the floor is ever lowered.

11. **Tuist `infoPlist` shortcuts** are NOT the raw `xcodebuild` `INFOPLIST_KEY_*` shortcuts — use `infoPlist: .extendingDefault(with: [...])` dictionary instead. Verify the generated plist has the document types.

12. **Test target discovery for `.metal` kernels:** unit tests cannot easily verify Metal compute output because Metal requires a GPU context. **Mitigation:** Phase 1 tests verify *structure* (RAWDecoder returns non-nil, MetalContext initializes, IOPModule conforms, LayerStack builds) — algorithmic correctness tests are Phase 2 golden-image harness (D-28). Use `@testable import LightamerCore` only when a genuinely internal type must be tested.

13. **Spike A outcome may invalidate the v1 iop list.** If RAW 9 demosaic is materially worse than Darktable on a target camera, the per-method demosaic port becomes a v1 hard requirement, expanding Phase 3 scope. **Mitigation:** run Spike A early (before Phase 3 planning); the spike report is a planning input.

14. **`any Layer` existential overhead (§5b gotcha).** The `LayerStack` holds `[any Layer]` — boxing overhead. Irrelevant for Phase 1's skeleton (no traversal). **Mitigation:** revisit as a Phase 6 perf decision; consider a concrete `AdjustmentLayer` struct if profiling shows the boxing matters in the hot composite loop.

## Open Questions for Planning

Decisions the planner still needs to make (not already locked in CONTEXT.md):

1. **`RAWDecoder` actor vs. `@unchecked Sendable` class?** Actor is safer (compiler-enforced isolation) but adds hop overhead per property access. Class with internal locks may be faster but requires manual discipline. **Recommendation:** actor — Swift 6 strict concurrency favors it; decode latency dominates over actor hops.

2. **Where does `MetalContext` live in the dependency graph?** Owned by the App `@State`? A singleton? Injected into `EditorState`? **Recommendation:** inject via SwiftUI Environment or pass explicitly — avoids global mutable state. The `EditorState.load` takes `decoder:` and the render path takes `metal:` as parameters.

3. **PSO cache eviction policy?** D-16 says "lazy + memory cache" but doesn't specify LRU vs. unbounded. With ~91 modules × N specialization variants, the cache could grow. **Recommendation:** LRU bounded at, say, 256 entries. Phase 3+ validates the actual working set.

4. **String Catalog zh/en — do we ship both in Phase 1?** SYS-05 is Phase 13, but the *infrastructure* (the `.xcstrings` file) is cheap to add now. **Recommendation:** add the catalog with English source strings only; defer zh translation to Phase 13. Put it in the app target's `Resources/` (D-04).

5. **`AppError` enum exhaustiveness — what categories?** D-25 says "RAW/Metal/Session tiers" but the Phase 1 surface is narrower. **Recommendation:** enumerate Phase 1 errors (`.unsupportedFile`, `.decodeFailed`, `.metalDeviceUnavailable`, `.metalPSOFailed`, `.memoryExceeded`, `.cancelled`) and design for extension (Swift `case` exhaustion with `@unknown default` in switches).

6. **Spike deliverable artifact format.** D-06 says "report doc + golden samples + verification app code." Where do these live? **Recommendation:** under `.planning/spikes/spike-a-ciraw9-boundary/` and `.planning/spikes/spike-b-100mp-perf/`, with the verification app code in a sibling `app/` subdir. Golden samples in `app/samples/`.

7. **Should Phase 1 ship the `IOPColorspace` enum and a minimal `colorin`/`colorout`/`gamma` stub?** The terminal trio is Phase 2 (per ROADMAP), but if the Phase 1 no-op pixelpipe needs *something* at the end to produce displayable output, a stub may be required. **Recommendation:** keep Phase 1 strictly to the pass-through; the CIRAW output is displayable as-is (it's already gamma-encoded for screen). Phase 2 introduces the linear-pipe terminal trio.

8. **macOS 27 SDK + Tuist version availability for the build environment.** The user's machine must be running macOS 27 beta AND have a Tuist version whose `ProjectDescription` supports the modern `Target.target(destinations:...)` API. **Flag for the planner:** confirm both before Phase 1 execution begins; if the Tuist version is older, fall back to the `Target(name:platform:...)` initializer form (mechanical translation).

9. **App icon and asset catalog.** No explicit CONTEXT decision. **Recommendation:** add `Resources/Assets.xcassets` (in the app target) with a placeholder app icon — required for notarization later (Phase 13) and trivial to add now.

10. **Should `LightamerCore` ship its own `.metallib`, or should all `.metal` files live in the app target?** **Recommendation:** Core ships its own `default.metallib` (in `LightamerCore/Resources/`) so that iop kernels in LightamerIOP can ALSO be self-contained (each iop ships its `.swift`+`.metal` pair in `LightamerIOP/Sources/`). The app target's `Resources/` holds app-level assets (String Catalog, app icon, fixtures) — NOT iop kernels. This keeps each module self-contained and avoids a "where does this kernel live" ambiguity. **Verify in Spike B:** can a framework target's metallib be loaded by the app at runtime? (It should — framework bundles are self-contained.)
