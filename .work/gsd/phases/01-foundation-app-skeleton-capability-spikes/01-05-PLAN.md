# Plan 05 — Spike A (CIRAW 9 boundary) + Spike B (100MP Metal perf): independent branches, minimal apps, reports

## Goal

Run the two research-flagged capability spikes on **independent branches** (D-06) using **self-contained minimal verification apps** (NOT the main Lightamer app — they depend on neither LightamerCore nor LightamerIOP). Each spike produces a report doc + golden samples that become planning inputs:

- **Spike A (CIRAW 9 capability boundary):** determine, per camera family, which demosaic/denoise/lens features RAW 9 covers natively vs. which need a Metal port. **Outcome determines whether the per-method demosaic menu (PPG/RCD/AMaZE/VNG4/Mark.3-pass/dual) is a v1 hard requirement** (a large Metal port) or can defer to Apple-default — directly affecting Phase 3 scope.
- **Spike B (100MP Metal performance vertebra):** confirm 60fps feasibility at zoom/pan on a 100MP GFX100S RAF before committing the iop list. Tests the architectural vertebra (success criterion #4: "100MP GFX100S RAF decodes + displays without jetsam/memory failure"). **Outcome confirms or overturns D-20 (tiling deferred to Phase 2).**

Per D-06 + RESEARCH §8 module-placement note: spikes are throwaway self-contained apps but useful patterns (CIRAW probe pattern, MetalContext dispatch shape, signpost intervals) get back-ported into the real modules in Plans 02/03. Spike code does NOT import LightamerCore/IOP.

## Tracer vertebra mapping

Wave 2 plan #1. Spikes validate capability boundaries that Wave 1 (Plans 01-04) assumes. Spike A's outcome is a planning input for Phase 3 (Tone & Filmic). Spike B's outcome is a planning input for Phase 2 (pixelpipe cache + tiling decision). Both run on isolated branches and do not block the Wave 1 vertebra — they can run in parallel with Wave 1 execution.

## Must-haves (goal-backward verification)

- [ ] Spike A runs on branch `spike/ciraw9-boundary`; Spike B runs on branch `spike/100mp-perf` (D-06).
- [ ] Each spike is a self-contained minimal SwiftUI macOS 27 app (its own `Project.swift` under `.planning/spikes/<spike>/app/`); neither imports LightamerCore or LightamerIOP.
- [ ] Spike A probes `supportedDecoderVersions` + visual diff (RAW 8 vs RAW 9) + timing + memory + no-op keys + lens coverage for ~12 sample files spanning Bayer pro/consumer, X-Trans, Quad-Bayer, DNG. Report commits to `spike-report-A.md`.
- [ ] Spike B decodes + displays a 100MP GFX100S RAF with zoom/pan, measuring decode time, display time, memory peak, drag fps, GPU working set. Report commits to `spike-report-B.md`.
- [ ] Spike A decision: per camera family, is Apple-default demosaic acceptable for v1, or does the per-method demosaic menu become a v1 hard requirement?
- [ ] Spike B decision: is 100MP viable without tiling in Phase 1? (Confirms or overturns D-20.) Identify the MP threshold above which tiling becomes mandatory.
- [ ] Golden image samples (100% crops of torture regions) checked into each spike's `samples/` dir.
- [ ] `os.signpost` intervals emit on both spikes' decode/display paths (D-31).

## Reversibility gates

- **D-06 (spike deliverable form) — REVERSIBLE.** Independent branches + minimal apps + reports. No one-way decisions here; the spikes' *outcomes* may trigger re-litigation of D-20 (tiling) or Phase 3 scope, but those are downstream planning decisions, not locks in this plan.
- **D-20 (tiling deferred to Phase 2) — REVERSIBLE** but Spike B is the explicit mechanism to overturn it. If Spike B fails the memory/fps budget, escalate to re-litigate D-20 before Phase 2 planning.

No `checkpoint:decision` task in this plan — the spikes ARE the decision-gathering mechanism; their reports feed downstream checkpoints.

## Task 01-05-02 — Spike B: 100MP Metal performance vertebra (branch spike/100mp-perf)

**read_first:**
- `.planning/phases/01-foundation-app-skeleton-capability-spikes/01-RESEARCH.md` — §8 "Spike B: 100MP Metal Performance Vertebra" (full methodology — sample files [GFX100S RAF ~11650×8738, Sony A7R V ARW ~60MP, Canon R5 CR3 ~45MP]; hard budgets D-32; what to measure; report structure; decision criteria — Pass/Partial/Fail)
- `.planning/phases/01-foundation-app-skeleton-capability-spikes/01-CONTEXT.md` — D-20 (tiling deferred), D-30/D-32 (perf budgets: 100MP decode ≤2s, display ≤500ms, steady-state memory ≤4GB, drag frame ≤16ms)
- PITFALLS.md CIRAW-4 (lazy CIImage chain blowup; `cacheIntermediates: false` mitigation), METAL-4 (`.shared` storage on UMA), METAL-6 (100MP `.rgba32Float` ~1.6GB working-set check)

**action:**
1. Create branch `spike/100mp-perf` (D-06).
2. Create the spike app under `.planning/spikes/spike-b-100mp-perf/app/`:
   - `Project.swift` — a single-target Tuist macOS 27 app (`SpikeB`), no Lightamer dependencies.
   - `SpikeBApp.swift` + `ContentView.swift` — minimal macOS 27 app: open one RAF, decode via CIRAW, blit to MTKView. Add: zoom (scroll), pan (drag), `os.signpost` interval per frame, FPS counter overlay. Use `CIContext` with `cacheIntermediates: false` and the linear Rec2020 working space (matching FOUND-02) to validate the real config.
3. Stage sample files under `.planning/spikes/spike-b-100mp-perf/app/samples/`: GFX100S RAF (the headline 100MP torture image), Sony A7R V ARW (~60MP upper Bayer baseline), Canon R5 CR3 (~45MP common pro body). Document source in `README.md`.
4. Measure against the D-32 hard budgets:
   - **Decode time:** CIRAW 8 vs CIRAW 9, via `os.signpost`.
   - **Memory peak:** Instruments Allocations during full decode. Specifically test: does a single 100MP `RGBA32Float` plane (~1.6GB) fit? Does the lazy `CIImage` chain blow up (CIRAW-4)? Confirm `cacheIntermediates: false` keeps memory bounded.
   - **Blit time:** `CIContext.render(_:to:)` into `MTLTexture(.rgba32Float)` — measure.
   - **Drag time:** while scrolling/panning, the MTKView should re-blit at 60fps (frame time ≤16ms at viewport resolution).
   - **GPU working set:** `device.recommendedMaxWorkingSetSize` — confirm the 1.6GB plane is under budget.
5. Write `.planning/spikes/spike-b-100mp-perf/spike-report-B.md` with the structure per RESEARCH §8 #6: per-resolution-row table (image | MP | decode time RAW 8/9 | memory peak | blit time | drag fps | notes); the decision (is 100MP viable without tiling in Phase 1? — confirm or overturn D-20); identify the threshold (e.g. >80MP?) above which tiling becomes mandatory.
6. Save golden samples (decoded output PNGs at viewport resolution) into `app/samples/golden/`.

**acceptance_criteria:**
- Branch `spike/100mp-perf` exists.
- `.planning/spikes/spike-b-100mp-perf/app/Project.swift` exists and declares a single-target macOS 27 app with NO Lightamer dependency.
- `.planning/spikes/spike-b-100mp-perf/app/samples/` contains the GFX100S RAF + Sony A7R V ARW + Canon R5 CR3.
- `.planning/spikes/spike-b-100mp-perf/spike-report-B.md` exists with: the per-resolution-row table populated for all three samples; an explicit decision statement answering "is 100MP viable without tiling in Phase 1?"; the MP threshold for mandatory tiling.
- The report records: decode time, memory peak (with explicit confirmation that `cacheIntermediates: false` bounds it), blit time, drag fps, `recommendedMaxWorkingSetSize`.
- `os.signpost` intervals used for all timing.
